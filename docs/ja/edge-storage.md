# エッジストレージとオブジェクトストレージのコミット

この文書では、オブジェクトストレージとエッジランタイムを対象とする将来のストレージモデルを分離して記述します。

この設計は、現在のtxBASEの機能ではありません。

## 1. 現在の境界

現在のストレージ境界は、ローカルで範囲指向です。

DBFと草案段階のXBFは、ファイル、サイドカー、WALレコード、ローカル置換規則を使います。

オブジェクトストレージが持つ基本操作は異なります。
不変オブジェクト、条件付き書き込み、コミット済み世代を識別するマニフェストが必要です。

オブジェクトストレージの設計では、別のデータベースモデルを作らず、既存のクエリ、更新、復旧の契約を保たなければなりません。

## 2. オブジェクト配置

候補となる配置は次のとおりです。

```text
table.meta
pages/
  000001
  000002
  000003
wal/
  00000042
```

マニフェストはコミット済み状態を識別します。

```json
{
  "generation": 142,
  "root": "pages/000031",
  "wal_head": 9482
}
```

ページとWALレコードは公開後に変更しません。

マニフェストが変更可能なコミット地点になります。

## 3. コミット手順

候補となるコミット手順は次のとおりです。

```text
不変ページを書き込む
      ↓
WALを書き込む
      ↓
マニフェストを条件付きで更新する
      ↓
コミットする
```

ETagまたは世代の事前条件で、同時書き込みに対するcompare-and-swap保護を提供できます。

マニフェスト更新に失敗しても、直前の世代は読み取れる状態を保たなければなりません。

読み取り側はページを読む前に1つのマニフェスト世代を解決し、1つの結果に複数世代を混在させてはいけません。

## 4. 必要な契約

実装前に、次の事項を定義しなければなりません。

- 読み取りの整合性と可視性。
- マニフェストのcompare-and-swap失敗時の動作。
- 再試行と冪等性の規則。
- 孤立ページと孤立WALの削除。
- 世代の保持とスナップショットの有効期限。
- 壊れたデータの検出と復旧。
- クラウドアカウントを必要としない決定的なローカルフィクスチャ。

これらの契約は、現在のローカルファイル置換が直接扱う失敗ケースを対象にします。

## 5. XBFとの関係

XBFは、不変ページと世代スナップショットを実装する自然なネイティブ形式です。

オブジェクトストレージのバックエンドは、意味が一致する範囲でXBFのチェックサム、スキーマ規則、クエリ意味論、トランザクション状態遷移を再利用します。

ストレージ固有のコードは、オブジェクトキー、条件付きマニフェスト更新、再試行、ガベージコレクションを担当します。

## 6. 完了条件

最初のオブジェクトストレージ実装は、次の条件を満たしたときに完了とします。

- マニフェストスキーマを1つ文書化している。
- 決定的なインメモリまたはローカルオブジェクトストレージのフィクスチャがある。
- 同時書き込みの競合テストがある。
- 読み取り世代の整合性テストがある。
- 再試行と孤立データ削除の動作がある。
- ページ、WAL、マニフェスト公開の中断に対する復旧テストがある。

それまでは、オブジェクトストレージのコミットを将来の作業として扱います。

## 7. 明示的な非目標

この文書は、R2アダプター、特定クラウドベンダー、マルチリージョン合意、または自動ガベージコレクション方針を約束しません。

これらの選択には、前述の契約とエンドツーエンドテストが必要です。
