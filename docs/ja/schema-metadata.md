# スキーマメタデータとローカル制約

DBF フィールド記述子は、従来のファイルレイアウトを記述します。

現代的なリレーショナル制約をすべて安全に置ける場所ではありません。

そこで txBASE は、DBF バイト列を変更せず、DBF フィールドフラグに実際以上の意味を持たせずに、兄弟ファイルへ任意のリレーショナルメタデータを保存します。

## 1. サイドカーの識別

`users.dbf` に対応するメタデータサイドカーは次のとおりです。

```text
users.txschema.json
```

サイドカーは任意です。

サイドカーがなければ、テーブルは従来の DBF のみの動作を保ちます。

サイドカーがあれば、`txbase schema`、`txbase verify`、パスからロードする更新、バックアップ、復元がメタデータを公開して保ちます。

現在のサイドカーは DBF とは独立してバージョン管理します。

```json
{
  "format": "txbase-schema",
  "version": 1,
  "fields": {
    "ID": {"primary": true},
    "NAME": {"not_null": true, "default": "Unknown"}
  },
  "checks": [
    {"AGE": {"$gte": 0}}
  ],
  "constraints": {
    "unique": [["NAME", "AGE"]]
  }
}
```

任意のルート `encoding` プロパティは、宣言済みの四つのマルチバイトコーデックに加えて、strict Shift_JIS、EUC-JP、GB18030、ISO-2022-JP を明示的に選びます。

受け付けるラベルは `windows-31j` または `cp932`、`shift_jis`、`shift-jis`、`sjis`、`gbk` または `cp936`、`euc-kr` または `cp949`、`big5` または `cp950`、`euc-jp`、`gb18030`、`iso-2022-jp` または `iso2022-jp` です。

txBASE はラベルを正規化し、`schema` 出力の `encoding_override` として有効名を報告します。

同じ有効名は `encoding_metadata.effective` でも得られます。

このオブジェクトは DBF の宣言、実効値、解釈元を報告します。

解釈元は言語ドライバー、明示的オーバーライド、既存のフォールバックのいずれかです。

パス対応コマンドは、呼び出し単位のオーバーライドとして `--encoding NAME` も受け付けます。

この値はサイドカーの値より優先され、その呼び出し中の読み書きに使われます。

DBF ヘッダーやメタデータサイドカーには保存しません。

未知のルートプロパティやフィールドプロパティは拒否します。

未知のフィールド名、未サポートの形式、未サポートのバージョンは、テーブルのロード時に拒否します。

## 2. 現在の制約スライス

現在のバージョンは次のフィールドプロパティを受け付けます。

| プロパティ | 動作 |
| --- | --- |
| `primary` | `unique` と `not_null` を暗黙に持ち、単一フィールドの主キーを一つだけ受け付ける |
| `unique` | 他のアクティブレコードがすでに使っている非 null 値を拒否する |
| `not_null` | insert、replace、patch、recall で JSON `null` を拒否する |
| `default` | insert でフィールドが省略されたとき、スカラー値を補う |
| `references` | カタログスコープの `TABLE.FIELD` 外部キー対象を宣言する |

任意のルート `checks` 配列は、すべてのテーブルレベル述語が一致しない候補レコードを拒否します。

任意のルート `constraints` オブジェクトは、有界な複合キーを受け付けます。

| プロパティ | 動作 |
| --- | --- |
| `primary` | 二つ以上のフィールド名を要求し、すべての値が非 null でタプルが一意であることを要求する |
| `unique` | 二つ以上のフィールド名の配列を受け付け、非 null のタプルがアクティブレコード間で重複することを拒否する |

サイドカーの `encoding` プロパティはフィールド制約ではありません。

レコードが JSON 層へ入る前に、文字の読み書きへ使うコーデックを選びます。

同じ八つのコーデックは、公開 API `DbfTable::from_path_with_encoding` または CLI の `--encoding` オプションで一時的に選べます。

照合や自動変換方針は追加しません。

制約は、メモリ上のレコードを変更する前に検査します。

スカラー `default` 値は insert で省略されたフィールドにだけ適用します。

明示的な JSON `null` は置き換えず、replace、patch、recall はすでに生成した候補値を使います。

既定値は `not_null`、一意性、`checks` の検証前に適用します。

複合一意制約は既存のスカラー比較規則を使います。

null を含むタプルは一意性に参加させず、既存の単一フィールド一意性と同じ動作にします。

`references` は、名前付き更新またはカタログトランザクションの後にディレクトリカタログが解決します。

非 null の子値は参照テーブルのアクティブレコードに一致しなければなりません。

null は許可し、子を孤立させる親の更新または論理削除を拒否します。

カタログは変更を連鎖させません。

パスだけの単一テーブル操作はテーブル間参照を解決できないため、このプロパティを強制しません。

既存のアクティブレコードはサイドカーのロード時に検査します。

そのため、既存の不正な DBF を制約付きの有効なテーブルとして黙って受け入れません。

削除済みレコードは一意性検査に参加しません。

`RECALL` は削除マーカーを除く前に、現在のアクティブレコードとの整合性を検査します。

各 `checks` 要素は `filter` と同じ有界な比較、所属、論理、`$expr` 規則を使うクエリ述語オブジェクトです。

サイドカーのロード時に checks を検証し、アクティブレコードとすべての insert、replace、patch、recall 候補に評価します。

現在の実装はスカラー数値を数値順で比較し、文字列と真偽値は JSON 値の意味論を使います。

## 3. 永続化の境界

DBF はフィールドバイト列の真実のソースです。

メタデータサイドカーは DBF と一緒にロードし、パスからロードしたテーブルの古いソース検査に含めます。

テーブルをロードした後にサイドカーが出現、消失、変更した場合、異なる制約集合の下で更新を適用せず保存を拒否します。

レコード更新によってサイドカーを書き換えることはありません。

`backup` と `restore` は `*.txschema.json` としてコピーし、ソースにない場合は宛先の古いメタデータサイドカーを削除します。

DBF とメタデータファイルは別々のファイルです。

現在のコピーと WAL プロトコルは、メタデータ編集を一つのアトミックな複数ファイルコミットにすることを主張しません。

## 4. 意図的な非目標

サイドカーはまだ次を実装していません。

- DBF フィールド記述子から独立した照合または型宣言。
- スキーマ移行またはメタデータ編集コマンド。
- DBF 言語ドライバーとオーバーライドの自動選択。

テーブル間制約を安全に追加するには、より広いメタデータ、移行、復旧規則が必要です。

SQLite の公式 [`CREATE TABLE` リファレンス](https://sqlite.org/lang_createtable.html)は、`NOT NULL`、`CHECK`、`UNIQUE`、`PRIMARY KEY`、`FOREIGN KEY` の制約を区別し、書き込み時の動作を文書化しています。

SQLite の[外部キーリファレンス](https://www.sqlite.org/foreignkeys.html)も、参照先テーブルの存在契約を明示します。

txBASE はそれらを設計上の参照としますが、SQLite 互換性は主張しません。
