# 分散化の進化

この文書では、レプリケーションと分散データベースの境界を分離して記述します。

txBASEには、プロセス内で完結するローカルなレプリケーションスライスと、有界なHTTP配送面があります。
バージョン付きエントリ、単一権威による再生、スナップショットインストール、バージョン付き転送の契約を定義しますが、クォーラムレプリケーションやコンセンサスは実装しません。

## 1. 前提条件

分散機能は、ローカルトランザクションとエッジストレージの契約が安定してから追加します。

現在の排他的テーブルロックは、合意、レプリケーション、マルチリージョン動作を意味しません。

最初に必要なのは、ローカルで復旧動作を検証済みの決定的な更新表現です。

現在のスライスは、`ReplicationEntry`と`ReplicationLog`でこの境界を提供します。
既存の`OperationIr`とカタログジャーナルを再利用し、2つ目の更新エンジンは作りません。

## 2. 推奨する進行順

実装順序は次のとおりです。

```text
細粒度WAL
      ↓
決定的な更新IR
      ↓
単一ライターの正しさ
      ↓
レプリケーションログ（現在のローカル再生スライス）
      ↓
有界なHTTPエントリおよびスナップショット配送（現在の転送スライス）
      ↓
Raftまたは選択した別の権威プロトコル
```

各段階は、次の段階が依存する前に独立した契約を持たなければなりません。

## 3. レプリケーションエントリ

バージョン1のログエントリには、次の情報を含めます。

```text
version
term
index
transaction ID
catalog representation tag
operation IR
```

`ReplicationEntry`はこの形をJSONとしてシリアライズします。
未知のフィールド、未対応バージョン、読み取り操作、空のバッチ、0以下の位置を拒否します。
カタログ表現タグによって、異なるカタログイメージへの適用を防ぎます。

`ReplicationLog`は、ローカル権威用の固定termを1つ選びます。
`propose`は既存のカタログジャーナルでバッチをcommitし、commit成功後にだけ記録します。
次の`TXRP`サイドカーのイメージも同じカタログtransactionに含めるため、カタログデータとローカルのレプリケーション位置は一緒に復旧します。
`receive`は次のindexとtransaction IDだけを受け付け、termと表現タグを検査してから、同じ原子的なカタログcommitを適用します。

エントリ形式では、同じ内容の重複配送をno-opとして扱います。
内容が異なる重複、indexまたはtransaction IDの欠落、term不一致、利用できない履歴の先頭は、新しいcommitの前に拒否します。

メモリ上のJSON形式は、転送に依存しないフィクスチャのために利用できます。
耐久性のある`TXRP`サイドカーは、4バイトの`TXRP`マジック、サイドカー形式のバージョンバイト、検証済みの`ReplicationLog` JSONペイロードで構成します。
`ReplicationLog::open`はサイドカーを読み込み、要求されたtermとカタログtransaction位置を検査します。
サイドカーがない場合は、カタログ位置が一致するときだけ初期化します。

`read_at`は、要求されたtransactionが適用済みログに含まれ、ログ位置と稼働中のカタログ位置が一致するときだけ、保持された`Catalog::from_path_at`イメージを返します。
`read_applied`は、その条件を満たす最新のイメージを読み取ります。
これらはローカルの過去時点フォロワー読み取りを定義しますが、lease、linearizability、クォーラムによる鮮度、ネットワーク転送は提供しません。

### スナップショットインストール

バージョン1の`ReplicationSnapshot`は、固定term、最後のログindex、最後のカタログtransaction ID、カタログ表現タグ、1つのエンコード済みカタログMVCCイメージを含みます。
`ReplicationLog::snapshot`は、カタログread lock内で現在のカタログイメージを取得し、返す前にスキーマタグを検証します。
エンコード済みカタログペイロードの上限は64 MiBです。

`ReplicationLog::install_snapshot`は、変更前にバージョン、位置、スキーマ、termを検証します。
カタログジャーナルの1つのcommitを通じてDBF、memo、schemaファイルを置き換え、カタログMVCC履歴をインストールした基底へ戻し、カタログCDCとテーブル単位の一時的なMVCC、CDC、WAL、state、indexサイドカーを消去します。
同じcommitで一致する空の`TXRP`位置をジャーナル化します。
その後、メモリ上のログはスナップショットの次のindexとtransactionから再開します。

同じイメージの再インストールは、重複として確認します。
古いイメージ、同じtransactionに対する競合イメージ、サイドカーの相違、インストール中に変化したカタログは、部分的な置換を公開せずに拒否します。
これはローカル復旧のプリミティブです。
スナップショットの転送、ログ切り詰めの方針、権威による調整は、将来の分散契約に残します。

### HTTP転送境界

カタログサーバーは、構築済みのレプリケーションエントリまたはスナップショットを配送する、バージョン1のJSON境界を公開します。

| ルート | 契約 |
| --- | --- |
| `GET`または`HEAD /replication/status` | 転送バージョン、固定term、基底位置と最後の位置、現在のカタログ表現タグを返す。 |
| `GET`または`HEAD /replication/snapshot` | 検証済みの現在の`ReplicationSnapshot` JSONを出力する。 |
| `POST /replication/entry` | 1つの`ReplicationEntry`を検証して配送し、完全な重複を確認する。 |
| `POST /replication/snapshot` | 1つの`ReplicationSnapshot`を検証して原子的にインストールする。 |

エントリのリクエスト本文には、既存の1 MiB JSON入力上限を適用します。
スナップショットのリクエスト本文には、既存の64 MiBエンコード済みペイロード上限を適用します。
不正な文書は`422`を返し、term、位置、スキーマ、競合する重複、スナップショット状態の競合は`409`を返し、ストレージ障害は`500`を返します。
応答には転送バージョンを含め、適用操作では結果のindexとtransaction IDも含めます。

これは配送境界であり、leader選出プロトコルではありません。
既定の`authority`ロールは`/transaction`と名前付きテーブルの更新ルートを`TXRP`状態と同じカタログジャーナルcommitに捕捉し、commit前にテーブルETagを再検査します。
`follower`ロールは`status`で自身のロールを報告し、直接のカタログ更新を`409`で拒否しながらレプリケーション配送を受け付けます。
`TXBASE_REPLICATION_TOKEN`を設定すると、4つのレプリケーションルートにRFC 6750 Bearer認証が必要になり、認証情報がない場合または不正な場合は`WWW-Authenticate: Bearer`を伴う`401`を返します。
この環境変数を設定しない場合、ローカル開発との互換性のため、ルートは認証なしのままです。
転送にはTLS、ストリーミング、再試行キュー、バックプレッシャー、クォーラム、権威検出がありません。

## 4. 分散結合より先にデータを近接させる

分散リレーショナル機能では、まずデータの近接配置を優先します。

候補となるパーティションキーは次のとおりです。

```text
tenant_id
workspace_id
user_id
```

関連するテーブルは、可能な限り同じ場所に配置します。

```text
Shard A
├── user 1
├── posts for user 1
└── comments for user 1
```

これにより、結合がネットワークシャッフルになる状況を減らせます。

本当の分散結合と分散トランザクションは、後の機能として扱います。

## 5. 必要な契約

ローカルスライスでは、最初の契約を次のように定義します。

- 権威は、1つのプロセス内のwriterと固定termである。クォーラムは主張しない。
- 競合と再試行では、同じ内容の重複を受け付け、内容が異なる重複と欠落を拒否する。
- スキーマバージョンは、commit前にカタログ表現タグを一致させる。
- 復旧では、フォロワーが不足した先頭エントリを再試行し、ジャーナル化した`TXRP`ログがプロセス再起動後に続行できる。
- フォロワー読み取りでは、適用済みログのtransactionに対応する保持済みカタログイメージを読み取れる。
- スナップショット復旧では、検証済みのカタログイメージを原子的にインストールし、次のログ位置から再開できる。
- 転送では、カタログサーバーがバージョン付きエントリとスナップショットのJSONを、有界なHTTPルートと明示的な競合ステータスで受け付ける。
- 権威捕捉では、既定の`authority`ロールが`/transaction`と名前付きテーブルの更新を`TXRP`状態とともにジャーナル化し、`follower`ロールが直接のカタログ更新を拒否する。
- 認証では、`TXBASE_REPLICATION_TOKEN`により4つのレプリケーションルートをRFC 6750 Bearer認証で任意に保護する。
- 決定的な障害フィクスチャでは、CIテストが2番目のエントリを先に配送してから復旧する。

次の契約は未確定です。

- カタログ表現タグから独立したスキーマ移行。
- TLS、ストリーミング、再試行、バックプレッシャー、権威が調整するログ切り詰め。
- 分散フォロワー読み取りの整合性と鮮度。
- 遅延と転送状態の可観測性。
- クォーラムとネットワーク障害の動作。

変更データキャプチャ、永続WAL履歴、レプリケーションは、同じ順序契約を共有します。

## 6. 完了条件

最初のローカルレプリケーションスライスは、次の条件を満たしています。

- 選択したローカル権威モデルが1つある。固定termの単一writerである。
- バージョン付きの`ReplicationEntry`と`ReplicationLog`形式がある。
- termとカタログ位置を検査するジャーナル化された`TXRP`サイドカーがある。
- 適用済み位置を検査するローカルの過去時点フォロワー読み取り境界がある。
- バージョン付きスナップショットの出力と、古いイメージ、競合、並行変更を拒否する原子的なインストールがある。
- スナップショットインストール後に、カタログ履歴を基底化し、`TXRP`の基底位置を復旧できる。
- 再生、重複配送、競合、順序検査の決定的なテストがある。
- パーティションによる欠落、シリアライズ済みログの復旧、term、表現タグのテストがある。
- スナップショットの往復、インストール、再開、古いイメージ、競合を検査するテストがある。
- 有界なHTTPステータス、エントリ配送、重複配送、スナップショットインストール、出力を検査するテストがある。
- 既定のauthorityによる更新捕捉、テーブルETagの再検査、followerの読み取り専用ロールを検査するテストがある。
- 書き込みの整合性保証を明示している。次のカタログtransactionだけがcommitできる。
- 外部インフラなしで失敗と復旧を再現できるleader/followerフィクスチャがある。

クォーラムレプリケーション、完全なMVCC調整、分散フォロワー読み取りの保証、分散パーティショニングは将来の作業です。

## 7. 明示的な非目標

この文書は、Raft、クォーラム、マルチリージョン書き込み、グローバルトランザクション、ネットワーク経由のログ切り詰め、分散フォロワー読み取りの保証、自動パーティション再配置を約束しません。

これらの選択には、前述の権威と復旧の契約が必要です。

- [Raft consensus algorithm](https://raft.github.io/)
- [RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)

Raft論文は、進行計画における権威プロトコルの候補資料です。
txBASEでRaftを採用することを決定するものではなく、将来のtxBASEログ、スキーマ、復旧形式も定義しません。

現在のリポジトリにはローカルのエントリと再生の実装、検証済みスナップショットインストール、ジャーナル化された`TXRP`サイドカー、有界なHTTP配送ルート、カタログ更新を捕捉する既定のauthority、読み取り専用のfollowerロール、適用済み位置を検査する過去時点フォロワー読み取り境界がありますが、コンセンサス、クォーラム、分散フォロワー読み取りの保証、分散結合の実装はありません。
これらの記述は、互換性の主張ではなく設計上の制約です。
