# 分散化の進化

この文書では、将来のレプリケーションと分散データベースの境界を分離して記述します。

この設計は、現在のtxBASEの機能ではありません。

## 1. 前提条件

分散機能は、ローカルトランザクションとエッジストレージの契約が安定してから追加します。

現在の排他的テーブルロックは、合意、レプリケーション、マルチリージョン動作を意味しません。

最初に必要なのは、ローカルで復旧動作を検証済みの決定的な更新表現です。

## 2. 推奨する進行順

実装順序は次のとおりです。

```text
細粒度WAL
      ↓
決定的な更新IR
      ↓
単一ライターの正しさ
      ↓
レプリケーションログ
      ↓
Raftまたは選択した別の権威プロトコル
```

各段階は、次の段階が依存する前に独立した契約を持たなければなりません。

## 3. レプリケーションエントリ

将来のログエントリには、次の情報を含めます。

```text
term
index
transaction ID
operation IR
```

更新と復旧の契約が安定した後は、完全なDBFファイルより論理更新を複製するほうが適しています。

エントリ形式では、冪等性、順序、重複配送、拒否、再生の動作を定義しなければなりません。

## 4. 分散結合より先にデータを近接させる

分散リレーショナル機能では、まずデータの近接配置を優先します。

候補となるパーティションキーは次のとおりです。

```text
tenant_id
workspace_id
user_id
```

関連するテーブルは、可能な限り同じ場所に配置します。

```text
Shard A
├── user 1
├── posts for user 1
└── comments for user 1
```

これにより、結合がネットワークシャッフルになる状況を減らせます。

本当の分散結合と分散トランザクションは、後の機能として扱います。

## 5. 必要な契約

実装前に、次の事項を定義しなければなりません。

- 権威とクォーラムのモデル。
- 競合と再試行の意味論。
- スキーマのバージョンと移行の動作。
- スナップショットインストールとフォロワー読み取りの規則。
- レプリケーションが部分的に失敗した場合の復旧。
- term、index、世代、遅延を観測する方法。
- パーティションとネットワーク障害用の決定的なローカルフィクスチャ。

変更データキャプチャ、永続WAL履歴、レプリケーションは、同じ順序契約を共有します。

## 6. 完了条件

最初の分散実装は、次の条件を満たしたときに完了とします。

- 選択した権威プロトコルが1つある。
- バージョン付きレプリケーションエントリ形式がある。
- 決定的な再生と重複配送のテストがある。
- パーティション、復旧、スキーマバージョンのテストがある。
- 読み取りと書き込みの整合性保証を明示している。
- 外部インフラなしで障害を再現できるエンドツーエンドフィクスチャがある。

それまでは、レプリケーション、完全なMVCC、フォロワー読み取り、分散パーティショニングを将来の作業として扱います。

## 7. 明示的な非目標

この文書は、Raft、マルチリージョン書き込み、グローバルトランザクション、自動パーティション再配置を約束しません。

これらの選択には、前述の権威と復旧の契約が必要です。
