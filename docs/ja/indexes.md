# セカンダリインデックスのサイドカー

現在のインデックススライスは、DBFファイルの外側に再構築可能なセカンダリインデックスを保存します。

`users.dbf`のサイドカーのパスは`users.txidx`です。

インデックスをDBFバイト列へ埋め込まないため、DBFは従来のxBaseツールから引き続き読み取れます。

## バージョン 3 の契約

インデックスファイルは、次のトップレベル形状を持つJSONです。

```json
{
  "format": "txbase-index",
  "version": 3,
  "source": {
    "dbf": {"length": 0, "hash": 0},
    "memo": null
  },
  "statistics": {
    "active_record_count": 0,
    "indexes": [{"name": "NAME"}]
  },
  "indexes": [
    {
      "definition": {"name": "NAME", "field": "NAME"},
      "entries": [
        {
          "key": {"kind": "scalar", "value": "Alice"},
          "records": [1]
        }
      ]
    }
  ]
}
```

複合定義では`field`の代わりに順序付き`fields`配列を使います。

```json
{"name": "by_name_age", "fields": ["NAME", "AGE"]}
```

バージョン3の複合定義には、フィールドごとに`1`または`-1`を1つ持つ`directions`配列を追加できます。

```json
{"name": "by_score_name", "fields": ["SCORE", "NAME"], "directions": [-1, 1]}
```

`directions`がない場合は、古いサイドカーとの互換性のため全フィールドを昇順とします。

範囲検索とヒストグラム境界は昇順キーを使うため、単一フィールドインデックスは引き続き昇順です。

実際の`length`と`hash`はDBFと検出したmemoサイドカーから生成します。

ハッシュはFNV-1aによる鮮度確認であり、真正性や改ざん防止の署名ではありません。

単一フィールドキーは文字列、数値、真偽値、明示的な`null`を受け付けます。

複合キーはそれらのスカラー領域による順序付きタプルで、宣言した各フィールドに1つの要素を持ちます。

配列とオブジェクトは、等値、順序、マルチキーの動作がまだ契約に含まれないため拒否します。

欠損フィールドと明示的な`null`は異なるインデックスキーです。

レコード番号は1始まりの物理DBFレコード番号です。

削除済みレコードはインデックスしません。

エントリは型付きキーの正規JSONエンコードでグループ化し、宣言したフィールド順で辞書順に並べます。

各要素の順序は`Missing`、`null`、真偽値、数値、文字列です。

表現可能な場合、数値は整数または浮動小数点の厳密な比較を使います。

1つのキー内のレコード番号は常に厳密な昇順であり、同じソートキーでもDBFの物理順を保ちます。

現在のサイドカーはアクティブレコード数とインデックスごとの統計を保存します。

各単一フィールドインデックスは、型付き値領域ごとに分けた等深度ヒストグラムを保存します。

各バケットには下限キー、上限キー、異なるキー数、インデックス済みレコード数があります。

複合インデックスはまだヒストグラムを保存しません。

## ライフサイクル

引数ごとに単一フィールドインデックスを1つ作成します。

```bash
txbase index build path/to/users.dbf NAME AGE
```

宣言したフィールド順で昇順の複合インデックスを1つ作成します。

```bash
txbase index build-compound path/to/users.dbf by_name_age NAME AGE
```

`:1`、`:-1`、`:asc`、`:desc`でフィールドごとの方向を追加します。

```bash
txbase index build-compound path/to/users.dbf by_score_name SCORE:-1 NAME:1
```

現在のDBFとmemoバイト列に対してサイドカーを検証します。

```bash
txbase index verify path/to/users.dbf
```

テーブル更新後に既存の定義を再構築します。

```bash
txbase index rebuild path/to/users.dbf
```

`index rebuild`は定義を読み取れる場合、バージョン1のサイドカーを現在の形式へ移行します。

バージョン1または2のサイドカーは、再構築されるまでクエリ計画には使いません。

`load`と`verify`は先にDBFを復旧し、保存されたソースフィンガープリントと比較します。

`.txidx`ファイルが存在する場合、通常のDBF永続化はDBFまたはmemoの対象と同じdurable WALに目標内容を記録します。

WALの状態レコードを同期してから対象サイドカーを置き換えます。

置換が中断された場合、起動時の復旧はWALをクリアする前にDBFまたはmemoの対象とインデックス対象を再実行します。

対象世代または適用処理を完了できない場合、DBFを真実のソースとして保ち、次の`load`または`verify`が古いか不正なサイドカーを拒否します。

DBFまたはmemoが変わった場合、誤ったレコード番号を返す代わりに古いインデックスエラーを返します。

再構築は既存サイドカーの定義を保ち、アクティブレコードからエントリを生成し直します。

書き込みは同期済みの一時ファイルを使い、その後`.txidx`パスを置き換えます。

`backup`と`restore`は存在する`.txidx`サイドカーをDBF、memo、スキーマサイドカーと一緒に検証してコピーします。

ソースインデックスは新鮮で構造的に正しくなければなりません。

古い、または壊れたソースは、誤ったレコード番号を使うのにクエリ可能に見えるバックアップを作らないため拒否します。

ソースにインデックスがなければ、古い宛先`.txidx`を削除します。

インデックスは派生状態なので、`.txidx`なしでバックアップを復元し、宛先で明示的に再構築できます。

## クラッシュ境界

現在の契約ではインデックスを派生状態として扱いますが、有効な既存サイドカーにはDBFまたはmemoと並ぶ永続的な復旧対象を与えます。

WALは対象を置き換える前に同期します。

復旧は対象レコードを冪等に再適用し、DBFとmemoの書き込みが完了してからWALをクリアします。

一致するソースフィンガープリントを持つインデックス対象は、通常のインデックス書き込みと同じ同期済み一時ファイル置換でインストールします。

クラッシュ後に古いか不正なサイドカーが見えても、クエリ計画が使う前にソースフィンガープリントと完全なエントリ検証で拒否します。

これは有効な対象レコードを対象とするWAL付きのクラッシュアトミック復旧契約です。

DBF、memo、インデックスファイルを1つのファイルシステムrenameで置き換える契約ではありません。

この契約は、リポジトリが使うファイル同期とディレクトリ同期をファイルシステムが実行することに依存します。

## 現在の境界

サイドカーは現在、作成、スカラーおよび複合キーの完全一致検索、複合等値プレフィックス候補検索、範囲候補検索、複合等値プレフィックス範囲候補検索をサポートします。
さらに、ヒストグラムによる範囲順序推定、単一フィールドの順序付き走査、複数キーソートの順序プレフィックス走査、フィールド方向ごとの複合キー構築とプレフィックス走査もサポートします。
複数単一フィールドインデックス間の等値候補の積集合、一様統計による等値候補の順序付け、単独インデックスと積集合のコスト選択、古さの検出、検証、再構築、通常の永続化または復旧後のWAL付き更新も対象です。

DBFの挿入、更新、論理削除、`PACK`、`RECALL`は、DBF保存が正常に完了すると既存サイドカーを更新します。

更新の永続化はDBFを置き換える前に既存サイドカーを検証します。

そのため古いか壊れたサイドカーがあればDBFを変更せず、インデックスエラーを報告します。

スキーマを保つXBFからDBFへのエクスポートも、既存サイドカーを新しいDBF状態と並ぶ`TXSE`対象としてステージします。

エクスポートは対象DBFから既存の定義を再構築し、復旧時にエントリとソースフィンガープリントを検証します。

XBF入力からインデックスをコピーすることはありません。

直接DBFを編集した場合、サイドカーは古いままになることがあります。

明示的な修復経路は`index rebuild`です。

サポート外のサイドカー定義または更新I/Oの失敗がある場合、スキーマを保つエクスポートはジャーナルを書き込む前に拒否されます。

パス対応のクエリ実行器は、検索が有効だと証明できる場合に等値、複合等値プレフィックス、等値積集合、範囲、複合等値プレフィックス範囲、単一フィールド順序、複合プレフィックス順序のサイドカー走査を使います。

その後、候補レコードへ通常のフィルターパイプラインを適用します。

複数キーソートでは、単一フィールドインデックスが最初のソートキー順を提供し、同値キーグループだけを残りのキーで安定ソートします。

要求されたソートフィールドが正確な等値プレフィックスの後で複合定義に一致する場合、プランナーは要求方向または完全な逆方向のインデックス順を直接消費できます。

範囲フィールドが複合定義の正確な等値プレフィックスの後にある場合、プランナーは一致する複合エントリを候補前処理に使えます。

複合範囲検索は、最初にサイドカーを連続した等値プレフィックス区間へ二分探索で狭め、その区間だけを走査します。

候補経路は範囲比較を通常の実行器に残すため、インデックス方向は走査順を変えますが範囲の意味論は変えません。

プランナーは、テーブルスキャンと有効な等値、範囲、対応する順序付き経路を、有界な整数コストで比較します。

テーブルスキャンのコストは、アクティブレコード数と残りのソート作業の合計です。

インデックス経路のコストは、正確な候補数、サイドカーのエントリ数から求めた有界な対数走査項、残りのソート作業の合計です。

インデックス積集合では、選択したサイドカーごとに走査項を1つ加えます。

要求された順序をそのまま提供する順序付き経路にはソート項がありません。

コストが同じ場合は、複合等値プレフィックスによる前処理よりもテーブルスキャンと既存のアクセス経路を優先します。

同数の複合候補では、最短の定義、安定した名前の順を選びます。

これはローカルなレコード数、走査、ソート作業のモデルであり、物理I/O、メモリ、キャッシュを含む完全なコストモデルではありません。

プランナーはアクティブレコード数を記録し、各単一フィールドインデックスの異なるキー数をエントリから導出します。

一様分布を仮定して等値候補数を推定し、その推定順に候補インデックスを並べ、積集合候補の構築には正確なレコードリストを使います。

等値推定はローカル統計であり、有界なコストモデルへの入力です。

複数の範囲述語では、プランナーは重なるヒストグラムバケットで候補構築の順序を決め、その後、正確な範囲候補から最も低い有界コストを選びます。

重なったバケットは全体を数えるため、推定は意図的に粗くなります。

返すレコードを決めるのは引き続き正確な範囲候補です。

パスを持たない`QueryExecutor`実装はテーブルスキャンの参照経路です。

複合等値プレフィックス候補検索は、複合インデックスを連続した先頭キー区間へ狭め、物理レコード順で返します。

単一フィールドの範囲候補検索は型付きキー領域を狭め、下限と上限に対して二分探索を使います。

複合等値プレフィックス範囲検索は次のインデックス要素を絞り込み、通常のフィルターパイプラインの前に物理レコード順で返します。

候補レコード番号はなお具体化し、通常のフィルターパイプラインの前にDBFの物理順で並べます。

`IndexFile::load`は2つ目の完全なエントリベクターを再構築せず、読み込んだソート済みエントリに対してアクティブなDBFレコードを1つずつ検証します。

freshnessの検証では引き続きDBFとmemoのバイト列を読み取り、クエリ実行器も候補レコード番号を具体化するため、ゼロコピーやエンドツーエンドのindex I/Oを主張するものではありません。

I/Oを考慮した完全なコストモデル、照合対応計画、テーブル間インデックス定義またはクエリ計画には個別の契約が必要です。

等値、等値積集合、統計順、ヒストグラム順の範囲、複合プレフィックス範囲、単一フィールド順のプランナーをテストします。
順序プレフィックス、複合プレフィックス、非選択的なインデックスのテーブルスキャンフォールバックも、更新、復旧、古いインデックス、再構築、DBFとインデックスのWAL対象動作と一緒にテストします。

より広いインデックス対応には、I/Oを考慮した完全なコストモデルとテーブル間インデックスまたは計画の契約が必要です。
