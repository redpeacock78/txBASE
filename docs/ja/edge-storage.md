# エッジストレージとオブジェクトストレージのコミット

ローカルオブジェクトストレージ境界と、クラウドアダプター境界を定義します。

ローカル境界には、同じ世代、条件付き公開、再試行、復旧、過去世代の読み取り、明示的な保持の契約を検証するインメモリフィクスチャと、永続的なファイルシステムバックエンドがあります。

R2アダプターやその他のクラウドプロバイダー実装は、この境界に含めません。

## 1. 現在の境界

ネイティブのDBFとXBFの経路は、ローカルファイルとサイドカーを使う実装として残ります。

`txbase::edge::ObjectTable<S>` APIは、XBFスナップショット向けに別のオブジェクトストレージcommit境界を提供します。

`MemoryObjectStore`は、変更後に内容を変えないオブジェクト公開と、マニフェストのcompare-and-swapを実装した決定的なフィクスチャです。

`FilesystemObjectStore`は、同じ契約を1つのディレクトリに永続化します。
親ディレクトリを作成し、排他的な作成で変更後に内容を変えないオブジェクトを公開し、ロックファイルでストア操作を直列化し、同期済み一時ファイルでマニフェストを置き換えます。
ファイルシステムバックエンドはローカルの永続アダプターであり、クラウドプロバイダーの整合性を保証しません。

`AsyncObjectStore`は、5つの基本操作をランタイムから独立したfuture境界として定義します。
`SyncObjectStoreAdapter`は、既存の同期ストアをready済みfutureとして公開するため、ネイティブテストはexecutorを選ばずに非同期契約を検証できます。
`AsyncObjectTable`は、このfuture境界を通じてマニフェスト、世代、復旧、保持、孤立オブジェクト削除の規則を再利用します。
`with_limits`は、公開前のスナップショットエンコードと読み取り時のスナップショットデコードの両方に、設定したXBF上限を適用します。
同期アダプターはファイルI/Oを非ブロッキングにはしませんが、executorを選ばずに同じ高レベルプロトコルを検証できます。

`AsyncObjectTable::query_stream`は、`AsyncObjectStore`を通じて現在の復旧済みコミット済みスナップショットを読み取り、既存のクエリスナップショットストリームを再利用する`AsyncObjectQueryStream`を返します。

`AsyncObjectTable::query_stream_at(generation, request)`は、同じ境界を通じて保持中のコミット済み世代を1つ選択します。

最初のポーリングは`Pending`になることがあります。
読み込み完了後、ストリームはDBFで表現できる安定したスナップショットを所有し、filter、projection、skip、limitだけを受け付けます。

対応しないストリーム制御は、非同期ストレージの読み取りを開始する前に拒否します。

現在または保持中のスナップショットがない場合、または既存のDBF出力契約で表現できないXBF値は、クエリエラーの項目を1つ返してからストリームを終了します。

`wasm32`では、`WasmObjectTable`がJavaScriptのホストオブジェクトに同じ非同期テーブルプロトコルを委譲します。
ホストはPromiseを返す`get`、`putIfAbsent`、`compareAndSwap`、`delete`、`list`を提供します。
アダプターは、生成した`wasm-bindgen`ラッパーを通じて、XBFバイト列、マニフェスト検査、commit、過去世代読み取り、復旧、保持、孤立オブジェクト削除を公開します。
同じラッパーは、現在世代向けの`query_stream_json`と、保持世代を選ぶ`query_stream_json_at`も公開します。
各メソッドは選択したスナップショットを読み込み、変換した後に解決し、共有する所有型クエリストリームを返します。
タグ付きホスト拒否コードを共有するオブジェクトストレージエラー分類へ変換しますが、タイムアウト、キャンセル、再試行、転送の方針はホストの責務です。

`createWorkerObjectStore`は、これら5つの操作にWorker互換のHTTP転送を提供します。
Web Fetch API、標準の条件付きリクエストヘッダー、強いSHA-256 ETag、`AbortSignal`、有界なリクエストタイムアウトを使い、Rustコアへクラウドベンダーの依存を追加しません。
生成したWASMラッパーを介する決定的なローカルHTTPフィクスチャをCIで検査します。

プロバイダー固有のリモートオブジェクトストレージアダプターは、`AsyncObjectStore`を直接実装して、XBFスナップショットと世代の規則を再利用できます。

## 2. マニフェストスキーマ

1つのテーブルは次のオブジェクト配置を使います。

```text
users/manifest.json
users/snapshots/0.xbf
users/snapshots/1.xbf
users/wal/1.json
```

マニフェストのスキーマはバージョン管理します。

```json
{
  "version": 1,
  "generation": 142,
  "root": "users/snapshots/142.xbf",
  "wal_head": 142,
  "history": [140, 141, 142]
}
```

`root`は変更後に内容を変えないXBFスナップショットを指します。

`generation`は可視のテーブル世代です。

`wal_head`は、このローカル実装で保留または公開されたWAL世代を指します。

`history`は、`ObjectTable::read_at`で読み取り可能なコミット済み世代を列挙します。
古いマニフェストではこのメンバーを省略できますが、次のcommitで履歴が書き込まれるまでは現在世代だけを公開します。

読み取りは、XBFに埋め込まれた世代とマニフェストの世代が異なるスナップショットを拒否します。

## 3. commit手順

`ObjectTable::commit`の手順は次のとおりです。

```text
変更後に内容を変えないXBFスナップショットをput-if-absentで書き込む
      ↓
保留WALオブジェクトをput-if-absentで書き込む
      ↓
マニフェストをcompare-and-swapで更新する
      ↓
保留WALオブジェクトを削除する
```

マニフェストのCASには、commit前に読み取ったバイト列をそのまま事前条件として使います。

異なる2つのwriterが同じ世代に異なるバイト列を公開した場合、片方が他方を無断で置き換えず競合になります。

同じ世代に同じスナップショットを再試行すると、`AlreadyCommitted`を返します。

スナップショットとWALの公開後にマニフェスト更新が失敗した場合、`ObjectTable::recover`はXBFの世代を検証し、記録された基底世代が現在も有効ならマニフェストのCASを完了します。

マニフェストの公開後にWAL削除が失敗した場合、復旧はスナップショットを二重適用せず、適用済みのWALだけを削除します。

読み取りは、`root`オブジェクトを読む前に1つのマニフェストを解決します。

rootオブジェクトは変更後に内容を変えず、埋め込まれた世代も検証するため、複数世代が混在した結果を受け入れません。

`ObjectTable::read_at`は、変更後に内容を変えないスナップショットオブジェクトから保持中のコミット済み世代を読み取ります。
保持処理によって世代が削除された後は、スナップショットを返しません。

## 4. 孤立オブジェクトの削除

`ObjectTable::cleanup_orphans`は、現在のマニフェスト履歴に列挙されたすべての世代と、現在の基底世代に続くWALが保持する保留rootを残します。

コミット済み履歴または復旧可能な保留commitに含まれない古いWALオブジェクトとスナップショットオブジェクトを削除します。

復旧可能な保留commitは削除しません。

`ObjectTable::retain_generations(keep_last)`は、最初に最新のコミット済み世代だけを含む圧縮済みマニフェストを公開し、その後で古いスナップショットを削除します。
マニフェストの更新にはcompare-and-swapを使うため、並行commitが発生した場合は、その世代を誤って削除せず保持処理を競合として失敗させます。
削除が中断しても、圧縮済みマニフェストが正となり、後続の孤立オブジェクト削除で残ったオブジェクトを削除できます。
自動実行しないため、アダプターはストレージサービスに合った保持期間と有効期限を選択できます。

## 5. XBFとの関係

オブジェクトストレージ境界は、エンコード済みXBFスナップショットを保存し、XBFのチェックサム、スキーマ検証、世代フィールド、デコード制限を再利用します。

新しいクエリ言語や更新モデルは作りません。

マニフェストを変更可能なcommit地点とし、スナップショットと保留WALオブジェクトは公開後に内容を変えません。

## 6. クラウドアダプターの境界

リモートアダプターには、次の事項を別途定義します。

- 条件付き書き込みと再試行のエラー対応。
- `get`、`list`、compare-and-swapの整合性保証。
- スナップショットの有効期限と世代保持。
- 認証とリクエスト制限。
- 孤立オブジェクト削除のスケジュール。
- クラウド固有の破損と可用性の動作。

これらは`MemoryObjectStore`やXBFコーデックの責務ではありません。

`FilesystemObjectStore`は、これらのテスト向けにローカル永続化フィクスチャを提供します。
ただし、ロックファイルとファイルシステムの耐久性は、リモートサービスの整合性契約の代わりにはなりません。

ローカルおよび非同期のオブジェクトテーブルテストは、エンコード上限の失敗がスナップショットまたは保留WALオブジェクトの公開前に発生することも検査します。

Worker Fetchアダプターは、[Worker Fetchオブジェクトストレージアダプター](worker-object-store.md)に記載したホスト管理HTTP形式を実装します。
リモートアダプターは、ブロッキングのネイティブクライアントには`ObjectStore`を、別のホスト管理クライアントには`AsyncObjectStore`を実装できます。
高レベルの非同期マニフェストプロトコルは、commit、復旧、保持、条件付き公開を実装します。
JavaScriptのWASMアダプターとWorker Fetchアダプターは、このプロトコル用のホスト管理クライアントのフィクスチャを提供します。
プロバイダー固有の整合性と再試行の動作は、この汎用転送の範囲外です。

非同期クエリアダプターは、ストレージからクエリへ渡す汎用経路を提供しますが、ホストのスケジューリング、キャンセルの伝播、タイムアウト、再試行の動作は選択しません。
Worker Web Streamsアダプターは需要を制御し、ストリームのキャンセル時に行の配送を停止しますが、実行中のオブジェクトストアfutureまではキャンセルできません。

## 7. 明示的な非目標

この実装は、R2アダプター、特定クラウドベンダー、WASIのクエリストリームスケジューリング、実行中のオブジェクトストア操作のキャンセル、ホスト固有のタイムアウトまたは再試行動作、マルチリージョン合意、自動バックグラウンドGC、変更後に内容を変えないページ分割、プロバイダー固有のクラウド接続型WASMホストを約束しません。

これらの機能は、ホスト固有の失敗動作を決定的なテストで定義した後に、マニフェストと世代の契約を再利用できます。

## 一次資料と適用範囲

- [POSIXの`rename()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/rename.html)
- [POSIXの`fsync()`](https://pubs.opengroup.org/onlinepubs/009695399/functions/fsync.html)
- [XBF v1形式草案](xbf.md)

POSIXの`rename()`と`fsync()`は、ローカルバックエンドの一時ファイル置換と同期経路に関係するファイルシステム資料です。
マニフェスト、世代、compare-and-swap、復旧、保持の規則はtxBASE固有の契約であり、クラウドプロバイダーの動作を主張するものではありません。

現在の実装契約にクラウドプロバイダーの資料はありません。リモートアダプターが選定されていないためです。
プロバイダー固有の資料は、実装時にアダプター固有の文書へ追加します。
