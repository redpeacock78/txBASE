# 結合モデル

txBASEは、通常のクエリで使うJSONのフィールド規則とプロジェクション規則を再利用する、有界なカタログ操作として関係結合を扱います。

結合の境界は、単一テーブルの集約およびテーブル間の更新トランザクションとは分離しています。

## 1. 有界ローカル結合

ライブラリは`txbase::query::join`を通じて1つの有界ローカル結合を公開します。

ロードマップにある関係形状を受け取り、2つのカタログテーブル間に1つ以上の等値条件を指定できます。

```json
{
  "from": "users",
  "join": {
    "type": "left",
    "table": "posts",
    "on": {
      "users.ID": {
        "$eq": {
          "$field": "posts.USER_ID"
        }
      }
    }
  },
  "filter": {
    "users.ACTIVE": true
  },
  "projection": {
    "users.NAME": 1,
    "posts.TITLE": 1
  }
}
```

`join.parse`はJSONを検証し、`join::execute`は`Catalog`から名前付きテーブルをロードします。

現在の結合型は`inner`、`left`、`right`、`full`、`semi`、`anti`、`cross`です。

結果はキーを`table.field`形式で修飾したフラットなJSONオブジェクトです。

一致しない左行は右テーブルのフィールドなしで残ります。

`right`結合では一致しない右行が左テーブルのフィールドなしで残ります。

`full`結合では、両方のテーブルで一致しない行を残します。

一致した行と一致しない左行は左テーブルの順序で出力し、その後に一致しない右行を右テーブルの順序で出力します。

`semi`は少なくとも1つの右行が一致したときに左行を1つ出力します。

`anti`は一致する右行がないときに左行を1つ出力します。

どちらも右テーブルのフィールドを出力しません。

`cross`は空の`on`オブジェクトを受け付け、左行と右行のすべての組を出力します。

フィルター前の候補ペア数は100,000までです。

欠損した結合キーと明示的な`null`は一致しません。

等値結合のプランナーは、左と右のアクティブ行数から候補ペアが64以下なら`NestedLoop`を選びます。

候補ペアが64より多い等値ステージでは、利用可能な戦略の有界コストを比較します。

`Hash`のコストは、両入力を一度ずつ走査する値と、その入力に必要なDBFの論理ページ数に、内側の等値マップを構築する有界の作業を加えた値です。

`IndexNestedLoop`のコストは、外側の行数に内側のインデックス検索の対数推定値と平均等値ファンアウトを掛けた値に、外側のDBF論理ページ数、インデックスサイドカーを一度読む論理ページ推定値、検索ごとの保守的なDBFレコード論理ページ推定値を加えたものです。

互換性のあるordered indexが両側で鮮度を保っている場合、`Merge`のコストは両入力を一度ずつ走査する値と、その入力に必要なDBFの論理ページ数に、2つのordered indexサイドカーの論理ページ推定値を加えたものです。

直接または多段の各候補には、フィルター前の結合候補行数の推定値とマテリアライズした行幅に基づく決定的な作業量も含めます。

各等値ステージでは、等値キーの出現数からロード済み入力のフィルター前の候補行数を正確に求めます。
外部結合の不一致行と、`semi`または`anti`の左レコードごとの1行もこの計算に含めます。
その後のフィルターによって実際の出力行数は減る場合があります。

推定値が最も小さい戦略を選び、完全な同点では`Merge`、`IndexNestedLoop`、`Hash`の順を優先します。

直接の単一キー等値結合または多段の単一キー等値ステージでは、インデックス付きテーブルを検索の内側に置きます。

多段の`right`ステージでは、インデックス付きの右テーブルを検索し、中間結果を出力する前に右側の物理順へ戻します。

直接および多段ステージでは、等値条件のフィールド順がインデックスのフィールド順と一致する場合、鮮度検証済みの複合インデックスも使えます。

両入力に互換性のある鮮度検証済みordered indexがある大きな直接等値結合では、有界コストが最も小さい場合にプランナーが`Merge`を選び、キーグループを照合した後に左主体または右主体の出力順へ戻します。

インデックスを利用できない場合（存在しない、古い、壊れている、またはハッシュ推定値より高い場合）は`Hash`を選び、`right`結合では左テーブル、それ以外では右テーブルについて1つのメモリ内等値マップを作ります。

`full`結合は、両側の鮮度検証済みordered indexが互換し、有界なmergeコストが選ばれる場合にordered indexのmerge経路を使います。

それ以外の場合は、有界なハッシュ経路へフォールバックします。

index nested loop戦略は使いません。

多段の`full`ステージは有界なハッシュ経路を使い、直接のordered index merge経路は使いません。

この選択器は、`right`以外では左行を外側にした出力順を、`right`では右行を外側にした出力順を保ちます。

結果が100,000行を超える場合は拒否します。

複数結合では必須の`join`オブジェクトが最初のステージとなり、任意の`joins`配列が左から右へステージを追加します。

追加ステージは中間行にすでに含まれる任意のテーブルを参照し、新しいテーブルを1つ追加できます。

テーブル名は重複できず、ステージ数は8までです。

各中間結果は100,000行までです。

これは互換インデックスのmerge経路を備えた、有界な行作業、論理ページ、フィルター前の基数、出力マテリアライズのコストモデルです。

ファイルシステムのレイテンシー、キャッシュ状態、ページ再利用は測定しません。

多段ステージは、推定基数、マテリアライズした行幅、論理ページ入力を次のステージのハッシュまたはインデックス検索の選択へ渡します。

多段ステージにはordered merge経路をまだ提供せず、ファイルシステムとキャッシュを考慮したmerge計画も契約外です。

単一テーブルHTTPサーバーは結合を公開しません。

カタログサーバーは`QUERY /join`で同じ読み取り専用境界を公開します。

テーブル間の書き込みとトランザクションはこの境界の外側です。

結合は既存の`filter`と`projection`の規則を受け付けますが、`sort`、ページング、集約、自己結合エイリアス、テーブル間トランザクションは受け付けません。

MongoDBの[`$lookup`ステージ](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/)を語彙の参照にします。

MongoDBは`$lookup`を一致する外部文書を配列で追加する左外部結合と説明しますが、txBASEは付属する結合計画に合わせてフラットな関係行を出力します。

MongoDBの文書は、外部側にインデックスがない結合の性能コストも説明しています。

そのため最初のスライスには結果数の上限を設け、プランナーレベルの性能を主張しません。
