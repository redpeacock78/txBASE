# XBF v1 フォーマット草案

XBF は txBASE が提案するネイティブスナップショット形式です。

この文書は互換性の主張ではなく、設計契約です。

リポジトリには現在、`txbase::xbf::{encode, decode}` による有界な v1 コーデック、`txbase::xbf::{from_dbf, XbfTable::from_dbf}` による有界な DBF から XBF への変換ヘルパー、`txbase::xbf::{read_path, write_path}` による耐久スナップショットヘルパーがあります。

コーデックは草案ヘッダー、セクションチェックサム、スキーマ、ディレクトリ、型付きレコード、制約、設定済みサイズ制限を検証します。

完全スナップショットの `.xwl` 経路は基底世代と対象世代を記録し、復旧時の世代不一致を拒否します。

`read_path` と `read_path_with_limits` はデコード前に保留された `.xwl` を復旧します。

そのため通常のスナップショットロードと CLI コマンドが古い世代を観測することはありません。

有界な `to_dbf` ヘルパーは表現可能なテーブルをメモリ内 DBF テーブルへ出力します。

完全な DBF スキーマ互換性や型互換性は主張しません。

`to_dbf_with_schema` はさらに `txbase-schema` JSON 値を返し、表現可能な `primary`、`unique`、`not_null` 制約を呼び出し側が管理するサイドカーへ保てます。

`save_dbf_with_schema` はその DBF とサイドカーをステージし、検証し、目的の DBF、スキーマ、memo サイドカー、耐久 `.txbase.state` 状態を耐久 `TXSE` ジャーナルでコミットします。

ジャーナルは正確な基底バイトを記録し、DBF、スキーマ、トランザクション状態をファイルごとの同期と置換で適用し、古い memo の種類を削除し、通常の DBF 読み取りが中断された出力を再開できるようにします。

復旧は、別の writer が変更した対象を上書きせず拒否します。

これはクラッシュ復旧と競合検出の境界であり、外部の従来リーダーがすべてのファイルを物理的に一つのアトミックスナップショットとして観測することは主張しません。

既存の `.txidx` サイドカーがある場合、出力は古い候補インデックスを残さず、コミット済み DBF 状態から更新します。

コーデックは意図的に形式層に閉じ込めています。

二つ目のクエリ実装や HTTP 実装は追加しません。

## 1. 目的と境界

DBF は従来の xBase データに対するインポート形式および保存形式として保ちます。

XBF は、DBF では損失なく表現できない次の制限を取り除きます。

- UTF-8 テキスト。
- 明示的な `NULL`。
- 可変長値。
- 符号付きおよび符号なしの現代的な整数。
- タイムスタンプとバイナリ値。
- txBASE が所有するスキーマメタデータ。

互換性は一方向の関係です。

```text
DBF -> XBF    DBF リーダーが元の値を表現できる場合は損失なし
XBF -> DBF    対象で表現可能かを検査した後だけ許可
```

XBF は DBF の拡張ではなく、既存 DBF バイト列の意味を変更しません。

## 2. ファイル集合

`users` という名前のテーブルに対する初期ファイル集合は次のとおりです。

```text
users.xbf       耐久スナップショット
users.xwl       任意のトランザクションログ
users.xidx      任意の外部インデックスサイドカー
```

スナップショットは自己記述的です。

圧縮済みスナップショットが無制限の履歴を保持しなくてよいよう、トランザクションログは分離します。

スナップショットバイトとディレクトリエントリが耐久的に書き込まれるまで、XBF ファイルはコミット済み世代を主張できません。

## 3. ヘッダー

以下で特に指定しない限り、すべての整数値は符号なしリトルエンディアンです。

v1 ヘッダーは正確に 100 バイトです。

| オフセット | サイズ | フィールド |
| ---: | ---: | --- |
| `0` | 4 | ASCII マジック `TXBF` |
| `4` | 2 | メジャーバージョン `1` |
| `6` | 2 | マイナーバージョン `0` |
| `8` | 4 | 機能フラグ。未知のビットはエラー |
| `12` | 4 | ヘッダー長 `100` |
| `16` | 8 | スキーマオフセット |
| `24` | 8 | スキーマ長 |
| `32` | 4 | スキーマセクションの CRC-32C |
| `36` | 8 | レコードディレクトリのオフセット |
| `44` | 8 | レコードディレクトリの長さ |
| `52` | 4 | レコードディレクトリの CRC-32C |
| `56` | 8 | レコードデータのオフセット |
| `64` | 8 | レコードデータの長さ |
| `72` | 4 | レコードデータの CRC-32C |
| `76` | 8 | レコード数 |
| `84` | 8 | スナップショット世代 |
| `92` | 4 | このフィールドをゼロにしたヘッダーの CRC-32C |
| `96` | 4 | 予約済み。ゼロでなければならない |

CRC-32C は Castagnoli 多項式、初期値 `0xffffffff`、最終 XOR `0xffffffff` を使います。

三つのセクションは重ならず、順序付けられ、ファイル内に完全に含まれなければなりません。

割り当て前に、オフセットと長さをオーバーフロー安全な算術で検査します。

未知のメジャーバージョンは拒否します。

新しいマイナーバージョンは、すべての機能フラグが既知で、宣言されたすべてのセクションを読み飛ばせる場合だけ受け付けます。

それ以外では黙ってダウングレードせず拒否します。

## 4. スキーマセクション

スキーマセクションは `u32` のフィールド数から始まります。

各記述子はフィールド順でエンコードします。

| サイズ | フィールド |
| ---: | --- |
| 2 | UTF-8 フィールド名の長さ `1..=255` |
| 可変 | UTF-8 フィールド名 |
| 1 | 型タグ |
| 1 | 制約フラグ |
| 2 | 予約済み。ゼロでなければならない |

制約フラグは次のとおりです。

| ビット | 意味 |
| ---: | --- |
| `0x01` | null 許容 |
| `0x02` | 主キーの構成要素 |
| `0x04` | 一意 |

重複名、不正な UTF-8、未サポートの型タグ、未知の制約ビットはエラーです。

最初の型タグ集合は次のとおりです。

| タグ | 型 |
| ---: | --- |
| `0x01` | 真偽値 |
| `0x10` | 符号付き 32 ビット整数 |
| `0x11` | 符号付き 64 ビット整数 |
| `0x12` | 符号なし 64 ビット整数 |
| `0x20` | IEEE-754 32 ビット浮動小数点 |
| `0x21` | IEEE-754 64 ビット浮動小数点 |
| `0x30` | UTF-8 文字列 |
| `0x31` | 任意バイト列 |
| `0x40` | UTC 日付。Unix epoch からの符号付き日数 |
| `0x41` | UTC タイムスタンプ。Unix epoch からの符号付きミリ秒 |
| `0x50` | Decimal。精度とスケールが定まるまで予約 |
| `0x60` | UUID。16 バイト |
| `0x70` | UTF-8 JSON 文書 |

`0x50` の decimal タグは v1 では予約済みであり、ワイヤー上の精度が定義されるまで拒否します。

最初の実装では、主キーとしてマークできるフィールドは最大一つです。

主キーのフィールドは暗黙に non-null かつ一意です。

複合キーは後続の形式バージョンに残します。

## 5. レコードディレクトリ

ディレクトリは `record_count` 個のエントリを正確に含みます。

各エントリは 24 バイトです。

| オフセット | サイズ | フィールド |
| ---: | ---: | --- |
| `0` | 8 | レコードデータの絶対オフセット |
| `8` | 8 | レコードペイロード長 |
| `16` | 4 | レコードフラグ |
| `20` | 4 | 予約済み。ゼロでなければならない |

レコードフラグ `0x01` は論理削除されたレコードを示します。

未知のレコードフラグはエラーです。

ディレクトリエントリはレコードデータセクションの中に完全に収まり、重なってはいけません。

レコード順は物理順です。

これは現在の DBF 層が使う識別モデルを保ちます。

## 6. レコードペイロード

ペイロードは、スキーマ順にすべてのスキーマフィールドの値を一つずつ含みます。

各値は次の形式です。

```text
value tag:    u8
payload size: u32
payload:      payload size bytes
```

タグ `0x00` は `NULL` を表し、ペイロード長は 0 でなければなりません。

non-null タグはフィールド型と一致しなければなりません。

ただし、表現可能な場合は整数フィールドにより幅の狭い符号付き整数タグを使えます。

真偽値ペイロードはちょうど一バイトで、`0` または `1` です。

UTF-8 値は有効な UTF-8 でなければなりません。

リーダーは割り当て前に、設定されたレコード単位または値単位の制限を超えるペイロードを拒否します。

末尾バイト、欠損フィールド、重複値、不正なスカラー幅はエラーです。

## 7. 検証と破損処理

リーダーは次の順序で検証します。

1. ヘッダーサイズ、マジック、バージョン、フラグ、ヘッダーチェックサム。
2. セクション境界と重複。
3. スキーマチェックサムと記述子。
4. ディレクトリチェックサムとエントリ。
5. データチェックサムとレコードペイロード。
6. 制約とレコード数の不変条件。

部分的にデコードされたテーブルをクエリ層へ公開しません。

チェックサムの失敗は空テーブルではなく破損です。

不正なスナップショットを最善努力で書き直して置き換えてはいけません。

コーデックはファイル、セクション、レコード、フィールド名、値のサイズに対する明示的な制限を公開します。

## 8. 世代とトランザクションログ

`generation` はコミット済みスナップショットの世代を識別します。

任意の `.xwl` ログは既存の txBASE 操作 IR とスナップショットレコードを含められますが、そのレコード形式は基底となった XBF 世代を記録しなければなりません。

現在のライブラリは、完全スナップショットレコードに対して `save_with_wal` と `recover_path` を提供します。

復旧は適用前に埋め込みスナップショットを検証し、すでにインストール済みの対象世代を冪等に受け付け、異なる現在世代を拒否します。

XBF 固有ヘッダーを含む WAL レコードは、トランザクション層の 16 MiB レコード制限に収まらなければなりません。

`write_path` は通常の XBF ファイル制限内ならより大きなスナップショットを永続化できますが、`save_with_wal` は `.xwl` ファイルを作る前に大きすぎる WAL レコードを拒否します。

復旧手順は、異なる基底世代を対象にするログを拒否しなければなりません。

通常の読み取り境界はこの手順を自動的に実行し、保留スナップショットの検証でも同じ設定済み XBF 制限を適用します。

最初の XBF 実装は完全スナップショット WAL レコードを使えます。

バイト差分と論理操作の再実行は、スナップショットプロトコルを証明した後の最適化です。

## 9. DBF 変換

現在の変換スライスはロード済み `DbfTable` を受け取り、メモリ内 `XbfTable` を生成します。

フィールド名、物理レコード順、削除フラグ、デコード済み値、DBF 層が表現するバイナリペイロード、DBF リーダーが区別できる null を保ちます。

`_NullFlags` などの DBF システムフィールドはユーザーフィールドとして公開しません。

DBF には txBASE 世代メタデータがないため、インポートした世代は `0` です。

未サポートまたは壊れた DBF フィールド値は、黙って強制変換せず変換を失敗させます。

このヘルパーだけでは XBF ファイルを書きません。

結果を `write_path` または `save_to` へ渡してください。

`DBF -> XBF` は次を保たなければなりません。

- フィールド名と値。
- DBF リーダーが区別できる明示的な null。
- memo とバイナリのペイロード。
- 不要な精度損失のない日付と数値の値。
- 対象が物理レコードを保つ場合の論理削除状態。

従来バイト列は XBF の UTF-8 テキストになる前にデコードします。

現在の `XBF -> DBF` 境界は、`C`、バイナリ `C`、`N`、`L`、`D`、Visual FoxPro `T` フィールドを持つメモリ内の従来 DBF テーブルをサポートします。

直接の `to_dbf` 経路は UUID と JSON 値、ASCII 以外または幅を超えるフィールド名、DBF フィールド制限を超える値、正確な数値範囲を超える符号なし整数、primary または unique 制約、NULL のテキストまたはバイナリ値を拒否します。

`to_dbf_with_schema` 経路は、DBF 値が表現可能なら primary と unique の制約を受け付け、サイドカーのメタデータを別に返します。

返された `DbfTable` は既存の `save_to` または `save_with_wal` 経路を使えます。

`XbfTable::dbf_export_report` は、ファイルを書き込まずに同じ DBF の基本表現可能性境界を検査します。

既知の変換問題を持つ全フィールドまたは物理レコード、テーブルがスキーマサイドカーを必要とするか、`representable` の真偽値を報告します。

このレポートは、直接の `to_dbf` 呼び出しが制約を保つことを主張しません。

`requires_schema_sidecar` が true の場合はスキーマ対応出力経路を使います。

`save_dbf_with_schema` はファイルレベルの便利な経路です。

CLI は `xbf export XBF DBF --schema` として公開します。

ファイルレベルの経路は対象の隣にジャーナルを書き、目的の対象をすべて適用してから削除します。

ジャーナルは DBF、スキーマサイドカー、DBT と FPT の両方の大文字小文字の形式をカバーするため、古い memo サイドカーを出力の一部として削除します。

通常の `DbfTable::from_path` 呼び出しは、レコードをロードする前に保留ジャーナルを復旧します。

既存の外部インデックスは同じ出力境界で更新します。

インデックスは派生状態であり、XBF 入力からコピーしません。

CLI は `xbf report XBF` も公開し、DBF やスキーマサイドカーを書かずに表現可能性レポートを表示します。

メモリ内変換は XBF 世代を永続化せず、サイドカー自身も書きません。

ファイルレベルヘルパーがジャーナルと復旧境界を所有するため、呼び出し側が二つ目のサイドカートランザクションを調整する必要はありません。

例には、可変長 UTF-8 テキスト、タイムスタンプ、UUID、未サポートの null 許容性、選択したコードページ外の文字があります。

損失のある出力を追加する場合は、明示的な別コマンドまたはフラグにし、適用した対応付けを報告しなければなりません。

## 10. 共有する上位層

クエリ、更新、プランナー、HTTP 層は、DBF と XBF で意味論が一致する範囲の内部レコードおよび操作契約を共有すべきです。

バイトレイアウト、チェックサム、型変換、スナップショット復旧を所有するのは形式層だけです。

これにより XBF が無関係な二つ目のデータベース実装になることを防ぎます。

## 11. 実装ゲート

草案コーデック、スナップショットライター、世代検査付き完全スナップショット WAL には現在、予約外の v1 型、破損検査、制約検査、明示的サイズ制限、同期と再ロードの往復経路をすべてカバーする決定的フィクスチャがあります。

XBF を完全にサポートする形式として宣伝する前に、リポジトリにはまだ次が必要です。

- 壊れたヘッダー、セクション、チェックサム、ディレクトリ、UTF-8、ペイロードのコーパス。
- DBF から XBF への往復テストと、XBF から DBF への表現可能性失敗テスト。
- スナップショット、`.xwl` 世代境界、`TXSE` スキーマ出力ジャーナルのクラッシュと復旧テスト。
- 従来リーダーから外部に見える厳密なアトミックスナップショット契約。現在の `TXSE` プロトコルは複数ファイル読み取りアトミック性ではなく、復旧可能性と競合検出を意図的に提供します。

これらのゲートがそろうまで、XBF は草案のままであり、サポート済み形式として宣伝しません。
