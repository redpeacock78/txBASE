# クエリモデル

txBASEは小さなJSONクエリ文書を使用します。

MongoDBは語彙と比較対象を提供しますが、互換性の目標ではありません。

クエリエンジンはDBFレコードをJSONにデコードした後、アクティブなレコードを評価します。

## 1. クエリ文書

現在の文書形状は次のとおりです。

```json
{
  "filter": {
    "AGE": {"$gte": 20, "$lt": 30},
    "COUNTRY": {"$in": ["JP", "TW"]},
    "$expr": {"$gt": ["$AGE", "$MIN_AGE"]}
  },
  "sort": {"AGE": 1},
  "projection": {"NAME": 1, "AGE": 1},
  "collation": "unicode-lowercase",
  "skip": 0,
  "limit": 100,
  "page_size": 25,
  "cursor": "42"
}
```

トップレベルのキーを検証します。

未知のキーは無視せず拒否します。

公開JSONクエリパーサーは、デシリアライズする前に`MAX_JSON_INPUT_BYTES`（現在は1 MiB）を超える文書を拒否します。

HTTP本文リーダーは大きすぎるリクエストに`413 Payload Too Large`を返し、RustとWASMの直接パーサー呼び出しは不正クエリエラーを返します。

`filter`の既定値は全件に一致するフィルターです。

`sort`では昇順に`1`、降順に`-1`を使用します。

任意の`collation`は`"unicode-lowercase"`、`"unicode-nfkc-lowercase"`、`"icu4x-2.1.1-ja"`、`"icu4x-2.1.1-zh"`、`"icu4x-2.1.1-ko"`を受け付けます。

`unicode-lowercase`は、比較前に文字列のソートキーをUnicodeの小文字へ変換します。

`unicode-nfkc-lowercase`は、UnicodeのNFKC互換正規化を適用してからソートキーを小文字へ変換します。

そのため、全角ラテン文字や半角カタカナなど、互換等価な形式は同じ値として比較します。

3つの`icu4x-2.1.1-*`値は、ICU4X 2.1.1の既定オプションで日本語、中国語、韓国語のロケール照合を使います。
既定のオプションは第3照合レベルを使います。
版を値に含めることで、カーソルと永続インデックス順が後続の照合契約へ暗黙に切り替わることを防ぎます。

ICU4Xモードが保証するのは選択したロケールの文字列ソートです。
それ以外の検索動作や、言語全体に対する辞書順互換性は主張しません。

省略した場合は既存のUnicodeコードポイント順を保ちます。

照合はソートだけに影響します。

フィルターとインデックス検索は既存の比較規則を保ちます。

照合を使うにはトップレベルの`sort`が空であってはならず、集約では使用できません。

一致する照合付きサイドカーが要求された順序を提供できます。

一致するサイドカーがなければ、プランナーはテーブルスキャンへ戻ります。

照合付きインデックスは順序だけを提供し、フィルター、完全一致、範囲検索は既存の比較規則を保ちます。

ソートカーソルは照合をエンコードし、異なるソート契約のトークンを拒否します。

`projection`では包含に`1`、除外に`0`を使用します。

`skip`と`limit`は0以上の整数です。

実行順序はフィルター、ソート、プロジェクション、スキップ、リミットです。

ソートキーが同値の場合はDBFのレコード順を保ちます。

任意の`aggregate`パイプラインの仕様は[集約モデル](aggregation.md)にあります。

`page_size`を指定すると、有界なカーソル応答を使用します。

```json
{
  "records": [{"NAME": "Alice"}],
  "cursor": "42"
}
```

物理ページの境界は、返したページの後ろにある1始まりのDBFレコード番号です。

物理カーソルは、その番号とテーブル表現のスナップショットタグを含む、バージョン付きの不透明なJSON文字列です。

次のリクエストは同じ`page_size`とトークンを送り、テーブル表現が変わっていない場合だけそのレコードの後から再開します。

`sort`を指定した場合、カーソルはバージョン付きのソートキー、スナップショットタグ、決定的な同値判定に使う最後の物理レコード番号を含みます。

次のリクエストは同じソートフィールドと方向を繰り返さなければなりません。

ソートカーソルはオフセットではなくキーセット境界です。

どちらのカーソルモードでも`skip`は併用できず、`page_size`は1,000以下に制限されます。

カーソル発行後にテーブルが変わった場合、異なる表現のページを結合せず無効なクエリエラーを返します。

これはカーソルのスナップショット整合性の境界です。
過去のテーブルスナップショットは、[MVCCと過去スナップショット](mvcc.md)で別に定義します。

パス指定の単一テーブル`QUERY /records`と`/explain`は、txBASEリーダー境界を使います。

実行前に通常のDBF復旧経路を完了し、共有テーブルロックを取得し、その保持中にDBF、memo、スキーマを再読み込みし、同じテーブルイメージに対してインデックスサイドカーを検証します。

writerは排他テーブルロックを使うため、txBASEリーダーが別のcommit世代のインデックスとテーブルイメージを組み合わせることはありません。

これはtxBASEリーダーに対する保証です。

ロックを無視する従来リーダーに対して、フラットなDBFとサイドカーを物理的にアトミックにはしません。

メモリ内クエリAPIと`QUERY /records/stream`は、渡されたテーブルとスナップショットストリームの契約を保ちます。

古いページを後続の読み手へ保持することはありません。

互換性のため、スナップショットタグを持たない従来の数値物理カーソルとv1ソートカーソルは引き続き受け付けます。

物理カーソルのページはアクティブなレコードを物理順に走査し、次ページの存在を示す追加の一致レコードを一件見つけるまでで止まります。

このモードではインデックス候補順を意図的に使わず、`explain_query_at`はテーブルスキャンを報告します。

これによりページの結果を有界に保ちます。

ソートカーソルのページは既存のソート比較を使い、一致するレコード参照を具体化してからページを選びます。

再開可能な結果境界は提供しますが、ストリーミングやバックプレッシャーは提供しません。

ライブラリは`query::stream_query`として、アクティブなレコードを読む借用型のpullベースイテレータを公開します。

このイテレータはレコードを消費しながら`filter`、`projection`、`skip`、`limit`を適用するため、一致するレコード集合を具体化しません。

ブロッキングまたは再開可能な結果境界を必要とする`sort`、`aggregate`、`page_size`、`cursor`は拒否します。

このイテレータは長寿命のスナップショットと非同期バックプレッシャープロトコルを提供しません。

`query::stream_query_snapshot`は安定スナップショット版です。

反復前にロード済みテーブルを複製するため、反復中に元テーブルを変更してもレコードは変わりません。

`query::stream_query_bounded`は所有型スナップショットイテレータを生成側スレッドで実行し、標準ライブラリの有界チャネルで項目を配送します。

チャネルが満杯の間は生成側が停止し、消費側をdropすると生成を停止します。

これはプロセス内のpull型消費側です。

ネイティブターゲットでは、`query::stream_query_threaded`が同じ所有型スナップショットをランタイム非依存の`AsyncQueryStream`契約で公開します。

`poll_next`ではブロッキングしない`try_recv`を使い、生成された各項目またはストリーム終了後に登録済みタスクを起こし、チャネル容量を生成側のバックプレッシャーとして適用し、非同期ストリームを破棄したときに生成側をjoinします。

これはネイティブホストアダプターです。ワーカーまたはWASIのタイマー、転送、非同期ストレージの動作は提供しません。

single-table serverは`QUERY /records/stream`を公開します。

catalog serverは`QUERY /{table}/records/stream`を公開します。

どちらのルートも同じJSONクエリ文書を受け付けますが、`filter`、`projection`、`skip`、`limit`だけを許可します。

成功した応答のメディアタイプは`application/x-ndjson`です。

各レコードをラッパー配列なしのコンパクトなJSONとして一行ずつ返します。

応答は`Content-Length`を省略するため、HTTP/1.1クライアントは有界生成側がレコードを提供するたびにチャンク転送データを受け取ります。

サーバーは生成側を開始する前にテーブルを複製し、`query::stream_query_bounded`と同じ正の容量を持つチャネルを使います。

クライアント接続を閉じると、応答readerの破棄によって生成を停止します。

不正な入力は、ストリーム開始前に通常の`400`、`415`、`422`応答で拒否します。

ストリームにはresume token、ETag、バイト範囲の契約がありません。

ヘッダー送信後の評価に失敗した場合は応答を終了し、クライアントはクエリ全体を再試行しなければなりません。

`query::AsyncQueryStream`は、長寿命クエリストリーム向けのexecutor非依存`poll_next`境界を定義します。

`QueryStream`と`QuerySnapshotStream`は、メモリ内データを即時にポーリングする実装です。

`BoundedQueryStream`は同期イテレータとして残ります。標準ライブラリの`recv`をポーリングするとホストのタスクをブロックするためです。

ネイティブスレッドアダプターは、スケジューリング、有界バックプレッシャー、waker通知、破棄時キャンセルを提供します。

`AsyncObjectTable::query_stream`は、復旧済みのコミット済みXBFスナップショットを1つクエリへ渡し、生存行を共有するJSONクエリ契約へ直接対応付けて、テーブル全体をDBFへ出力せずに所有型スナップショットストリームを再利用するランタイム非依存の非同期ストレージ経路を提供します。

ワーカーまたはWASIのスケジューリング、タイムアウト、キャンセル、転送、プロバイダー固有の非同期ストレージ動作は、引き続きホスト固有です。

完全な境界は[非同期クエリストリーム](async-streaming.md)に記載します。

## 2. 現在の述語語彙

| 分類 | 演算子 | 現在の規則 |
| --- | --- | --- |
| 比較 | `$eq`、`$ne`、`$gt`、`$gte`、`$lt`、`$lte` | エンジン固有の型規則でデコード済み JSON 値を比較する |
| 所属 | `$in`、`$nin` | 値を候補値のリストと照合する |
| 配列 | `$all`、`$elemMatch`、`$size` | 配列の内容、1つの配列要素の条件、または配列の正確な長さを照合する |
| 論理 | `$and`、`$or`、`$not` | 述語文書を合成または反転する |
| 式 | `$expr` | 同じレコードのスカラーリテラル、フィールド参照、`$literal`、2オペランドの`$ifNull`、有界な文字列`$concat` / `$toLower` / `$toUpper`、または有界な数値`$abs` / `$add` / `$subtract` / `$multiply` / `$divide` / `$mod`式を比較する |

空の`$and`はすべてのレコードに一致します。

空の`$or`はどのレコードにも一致しません。

欠損フィールドは、現在の実行器契約に従って`$ne`と`$nin`に一致します。

フィールドが配列の場合、配列要素の1つが述語を満たせば一致することがあります。

`$all`は配列オペランドを受け付け、空のオペランドはどのレコードにも一致せず、空でないオペランドは配列値のフィールドがすべての候補値を要素として持つ場合に一致します。

`$all`には有界な`$elemMatch`候補を含められ、各候補は1つの配列要素に一致しなければなりません。

`$elemMatch`は配列値のフィールドを要求し、1つの要素がすべてのスカラー演算子または同じ要素内のすべてのフィールド条件を満たす場合に一致します。

`$size`は0以上の整数を要求し、要素数が指定値と一致する配列だけに一致します。

これらの配列述語は有界なテーブルスキャンを使い、インデックス候補にはなりません。

これらの選択は`src/query/tests.rs`と`src/query/malformed_tests.rs`でテストします。

`$abs`は、数値リテラル、フィールド参照、またはネストした数値式を1つだけ受け付けます。

`$add`、`$subtract`、`$multiply`、`$divide`、`$mod`は、数値リテラル、フィールド参照、またはネストした数値式を2つだけ受け付けます。

`$literal`は、`$`で始まる文字列をフィールド参照として扱わずに、そのオペランドを返します。

`$ifNull`はスカラー式を2つだけ受け付け、最初の値が欠損または明示的な`null`の場合に2番目を評価します。

`$concat`はスカラー式を2つ以上受け付けます。解決した各オペランドは文字列でなければならず、欠損、`null`、文字列以外のオペランドは比較不一致になります。

`$toLower`と`$toUpper`は、文字列へ解決されるスカラー式を1つ受け付け、ロケールに依存しないUnicodeの大文字と小文字の変換を適用します。

共有スカラー式評価器を`$expr`と集計の`$set`/`$addFields`で使うため、フィールド、リテラル、nullフォールバック、文字列、数値式の意味論は両方の表面で同じです。

計算した文字列の結果は1 MiBまでです。上限を超える場合は、無制限の割り当てを避けてクエリエラーにします。

結果が収まる整数演算はJSONの整数を維持します。

混在型または小数の結果は有限なJSON数値でなければなりません。

割り切れる整数除算は整数を維持し、割り切れない除算は有限なJSON数値を生成します。

0による除算は拒否します。

0による剰余は拒否します。

選択した式が別の型を要求する場合、欠損、`null`、文字列以外、または非数値のフィールドオペランドは比較不一致になります。

整数オーバーフローと有限でない結果は拒否します。

これらはtxBASEの動作であり、MongoDB互換性として説明してはいけません。

## 3. パス、配列、プロジェクション

ドット区切りパスはネストしたJSONオブジェクトと配列をたどります。

数値のパス要素は明示的な配列インデックスを選びます。

数値でないパス要素は配列要素全体から一致するフィールドを訪れます。

完全一致するフィールド名はドット区切りの走査より優先されます。

プロジェクションは選択したフィールドを適用する前に形状を検証します。

現在の実装はMongoDBのすべてのプロジェクション規則、位置指定プロジェクション、`$elemMatch`プロジェクション、集約式を保証しません。
