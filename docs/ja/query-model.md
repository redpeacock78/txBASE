# クエリモデル

txBASE は小さな JSON クエリ文書を使用します。

MongoDB は語彙と比較対象を提供しますが、互換性の目標ではありません。

クエリエンジンは DBF レコードを JSON にデコードした後、アクティブなレコードを評価します。

## 1. クエリ文書

現在の文書形状は次のとおりです。

```json
{
  "filter": {
    "AGE": {"$gte": 20, "$lt": 30},
    "COUNTRY": {"$in": ["JP", "TW"]},
    "$expr": {"$gt": ["$AGE", "$MIN_AGE"]}
  },
  "sort": {"AGE": 1},
  "projection": {"NAME": 1, "AGE": 1},
  "collation": "unicode-lowercase",
  "skip": 0,
  "limit": 100,
  "page_size": 25,
  "cursor": "42"
}
```

トップレベルのキーを検証します。

未知のキーは無視せず拒否します。

`filter` の既定値は全件に一致するフィルターです。

`sort` では昇順に `1`、降順に `-1` を使用します。

任意の `collation` が現在受け付ける値は `"unicode-lowercase"` だけです。

この値を指定すると、比較前に文字列のソートキーを Unicode の小文字へ変換します。

省略した場合は既存の Unicode コードポイント順を保ちます。

照合はソートだけに影響します。

フィルターとインデックス検索は既存の比較規則を保ちます。

照合を使うにはトップレベルの `sort` が空であってはならず、集約では使用できず、計画は意図的にテーブルスキャンになります。

ソートカーソルは照合をエンコードし、異なるソート契約のトークンを拒否します。

`projection` では包含に `1`、除外に `0` を使用します。

`skip` と `limit` は 0 以上の整数です。

実行順序はフィルター、ソート、プロジェクション、スキップ、リミットです。

ソートキーが同値の場合は DBF のレコード順を保ちます。

パイプラインの末尾には、グループ出力に対する有界な `$sort` ステージを一つ置けます。

```json
{
  "aggregate": [
    {"$group": {"_id": "$COUNTRY", "count": {"$count": {}}}},
    {"$sort": {"count": -1, "_id": 1}}
  ]
}
```

件数だけを求めるパイプラインは、任意の `$match` ステージの後に終端 `$count` ステージを一つ置けます。

```json
{
  "aggregate": [
    {"$match": {"ACTIVE": true}},
    {"$count": "total"}
  ]
}
```

重複を除くパイプラインは、任意の `$match` ステージの後に終端 `$distinct` ステージを一つ置けます。

```json
{
  "aggregate": [
    {"$match": {"ACTIVE": true}},
    {"$distinct": "$COUNTRY"}
  ]
}
```

最後の `$limit` は `$sort` の後に置けます。

ソートを省略する場合は `$group` の後にも置けます。

```json
{
  "aggregate": [
    {"$group": {"_id": "$COUNTRY", "count": {"$count": {}}}},
    {"$sort": {"count": -1}},
    {"$limit": 10}
  ]
}
```

`page_size` を指定すると、有界なカーソル応答を使用します。

```json
{
  "records": [{"NAME": "Alice"}],
  "cursor": "42"
}
```

物理ページの境界は、返したページの後ろにある 1 始まりの DBF レコード番号です。

物理カーソルは、その番号とテーブル表現のスナップショットタグを含む、バージョン付きの不透明な JSON 文字列です。

次のリクエストは同じ `page_size` とトークンを送り、テーブル表現が変わっていない場合だけそのレコードの後から再開します。

`sort` を指定した場合、カーソルはバージョン付きのソートキー、スナップショットタグ、決定的な同値判定に使う最後の物理レコード番号を含みます。

次のリクエストは同じソートフィールドと方向を繰り返さなければなりません。

ソートカーソルはオフセットではなくキーセット境界です。

どちらのカーソルモードでも `skip` は併用できず、`page_size` は 1,000 以下に制限されます。

カーソル発行後にテーブルが変わった場合、異なる表現のページを結合せず無効なクエリエラーを返します。

これはスナップショット整合性の境界であり、過去の行バージョンを保持する MVCC ではありません。

古いページを後続の読み手へ保持することはありません。

互換性のため、スナップショットタグを持たない従来の数値物理カーソルと v1 ソートカーソルは引き続き受け付けます。

物理カーソルのページはアクティブなレコードを物理順に走査し、次ページの存在を示す追加の一致レコードを一件見つけるまでで止まります。

このモードではインデックス候補順を意図的に使わず、`explain_query_at` はテーブルスキャンを報告します。

これによりページの結果を有界に保ちます。

ソートカーソルのページは既存のソート比較を使い、一致するレコード参照を具体化してからページを選びます。

再開可能な結果境界は提供しますが、ストリーミングやバックプレッシャーは提供しません。

ライブラリは `query::stream_query` として、アクティブなレコードを読む借用型の pull ベースイテレータを公開します。

このイテレータはレコードを消費しながら `filter`、`projection`、`skip`、`limit` を適用するため、一致するレコード集合を具体化しません。

ブロッキングまたは再開可能な結果境界を必要とする `sort`、`aggregate`、`page_size`、`cursor` は拒否します。

このイテレータは長寿命のスナップショットも非同期バックプレッシャープロトコルも提供しません。

`query::stream_query_snapshot` は安定スナップショット版です。

反復前にロード済みテーブルを複製するため、反復中に元テーブルを変更してもレコードは変わりません。

`query::stream_query_bounded` は所有型スナップショットイテレータを生成側スレッドで実行し、標準ライブラリの有界チャネルで項目を配送します。

チャネルが満杯の間は生成側が停止し、消費側を drop すると生成を停止します。

これはプロセス内の pull 型消費側です。

single-table server は `QUERY /records/stream` を公開します。

catalog server は `QUERY /{table}/records/stream` を公開します。

どちらのルートも同じ JSON クエリ文書を受け付けますが、`filter`、`projection`、`skip`、`limit` だけを許可します。

成功した応答のメディアタイプは `application/x-ndjson` です。

各レコードをラッパー配列なしのコンパクトな JSON として一行ずつ返します。

応答は `Content-Length` を省略するため、HTTP/1.1 クライアントは有界生成側がレコードを提供するたびにチャンク転送データを受け取ります。

サーバーは生成側を開始する前にテーブルを複製し、`query::stream_query_bounded` と同じ正の容量を持つチャネルを使います。

クライアント接続を閉じると、応答 reader の破棄によって生成を停止します。

不正な入力は、ストリーム開始前に通常の `400`、`415`、`422` 応答で拒否します。

ストリームには resume token、ETag、バイト範囲の契約がありません。

ヘッダー送信後の評価に失敗した場合は応答を終了し、クライアントはクエリ全体を再試行しなければなりません。

ランタイム固有の非同期トレイトは別の将来境界です。

## 2. 有界集約

クエリ文書には、`filter` と 0 個以上の先行 `$match` ステージの後に、終端 `$count`、終端 `$distinct`、またはブロッキングな `$group` を一つ置けます。

```json
{
  "filter": {"ACTIVE": true},
  "aggregate": [
    {
      "$group": {
        "_id": "$COUNTRY",
        "count": {"$count": {}},
        "total_age": {"$sum": "$AGE"}
      }
    }
  ]
}
```

現在の集約境界は、0 個以上の `$match` の後に終端 `$count`、終端 `$distinct`、または `$group` を一つだけ受け付けます。

グループ出力には任意の `$project` を一つ、最後の `$sort` を最大一つ、最後の `$limit` を最大一つ置けます。

`_id` は `null` または一つのドット区切りフィールド参照です。

サポートするアキュムレータは `$count: {}`、`$sum: "$FIELD"`、`$min: "$FIELD"`、`$max: "$FIELD"`、および有限な JSON 数値に対する `$avg: "$FIELD"` です。

フィルターはグループ化より前に実行します。

結果は `_id` と名前付きアキュムレータフィールドを持つ JSON オブジェクトの配列です。

`$project` はクエリのプロジェクション規則を再利用してグループ出力のフィールドを包含または除外します。

`$project` は `$group` の後、`$sort` または `$limit` の前に置く必要があります。

包含と除外は混在できません。

プロジェクションは後続の `$sort` より前に適用するため、除外したフィールドをソートすると既存の欠損値順になります。

欠損したグループフィールドは `null` になります。

そのため欠損値と明示的な `null` は同じグループになります。

欠損、`null`、数値以外の `$sum` 入力は 0 として扱います。

このスライスは整数和を正確に保つため、小数は拒否します。

JSON の符号付き整数または符号なし整数で表せない整数和は拒否します。

欠損、`null`、数値以外の `$avg` 入力は無視します。

すべてが欠損または数値以外のグループは `null` を返し、非有限の累積結果は拒否します。

欠損と `null` の `$min` および `$max` 入力は無視します。

すべてが欠損または `null` のグループでは、そのアキュムレータは `null` になります。

非 `null` の `$min` および `$max` 値は、既存の JSON 順序規則で比較できなければなりません。

比較できない値は拒否します。

10,000 を超えるグループは拒否し、集約とトップレベルの `sort`、`projection`、`skip`、`limit`、cursor ページングの併用も拒否します。

`$sort` がない場合のグループ出力順は契約に含めませんが、現在の実装は決定的なキー順で出力します。

`$sort` は既存の JSON ソート順と安定した同値順を使います。

`$limit` は 0 以上の整数を受け付け、ソート後の具体化されたグループ結果を切り詰めます。

`$match` ステージはトップレベルの `filter` と同じ述語規則を使い、`$group`、`$count`、`$distinct` より前に置く必要があります。

`$count` は名前付きの 0 以上の整数フィールドを一つ持つ文書を返し、一致するレコードがない場合も 0 を返します。

`$distinct` は一つのフィールド参照を受け取り、重複しないフィールド値を JSON 配列で返します。

欠損フィールドと明示的な `null` は一つの `null` 値として扱います。

両ステージは終端であり、グループ出力ステージとは併用できません。

distinct 出力は 10,000 値までです。

`$limit` 後のステージ、追加の group、count、distinct ステージ、および式オペランドは未サポートです。

MongoDB は `$group` をブロッキングステージとして説明し、[$count と $sum を含む集約ステージの仕様](https://www.mongodb.com/docs/manual/reference/operator/aggregation/group/)を定義しています。

txBASE は MongoDB の完全なパイプライン互換性を主張せず、その別個の [`$count` ステージ](https://www.mongodb.com/docs/manual/reference/operator/aggregation/count/)を有界なステージとして表現します。

## 3. 有界ローカル結合

ライブラリは `txbase::query::join` を通じて一つの有界ローカル結合を公開します。

ロードマップにある関係形状を受け取り、二つのカタログテーブル間に一つ以上の等値条件を指定できます。

```json
{
  "from": "users",
  "join": {
    "type": "left",
    "table": "posts",
    "on": {
      "users.ID": {
        "$eq": {
          "$field": "posts.USER_ID"
        }
      }
    }
  },
  "filter": {
    "users.ACTIVE": true
  },
  "projection": {
    "users.NAME": 1,
    "posts.TITLE": 1
  }
}
```

`join.parse` は JSON を検証し、`join::execute` は `Catalog` から名前付きテーブルをロードします。

現在の結合型は `inner`、`left`、`right`、`semi`、`anti`、`cross` です。

結果はキーを `table.field` 形式で修飾したフラットな JSON オブジェクトです。

一致しない左行は右テーブルのフィールドなしで残ります。

`right` 結合では一致しない右行が左テーブルのフィールドなしで残ります。

`semi` は少なくとも一つの右行が一致したときに左行を一つ出力します。

`anti` は一致する右行がないときに左行を一つ出力します。

どちらも右テーブルのフィールドを出力しません。

`cross` は空の `on` オブジェクトを受け付け、左行と右行のすべての組を出力します。

フィルター前の候補ペア数は 100,000 までです。

欠損した結合キーと明示的な `null` は一致しません。

等値結合のプランナーは、左と右のアクティブ行数から候補ペアが 64 以下になる場合に `NestedLoop` を選びます。

直接の単一キー等値結合または多段の単一キー等値結合ステージで検索対象テーブルに鮮度検証済みの単一フィールドインデックスがある場合、候補ペアが 64 より多いと `IndexNestedLoop` を選び、外側の各キーをインデックスで検索します。

多段の `right` ステージでは、インデックス付きの右テーブルを検索し、中間結果を出力する前に右側の物理順へ戻します。

インデックスがない、古い、壊れている、または利用できない場合は `Hash` を選び、`right` 結合では左テーブル、それ以外では右テーブルについて一つのメモリ内等値マップを作ります。

この選択器は、`right` 以外では左行を外側にした出力順を、`right` では右行を外側にした出力順を保ちます。

結果が 100,000 行を超える場合は拒否します。

複数結合では必須の `join` オブジェクトが最初のステージとなり、任意の `joins` 配列が左から右へステージを追加します。

追加ステージは中間行にすでに含まれる任意のテーブルを参照し、新しいテーブルを一つ追加できます。

テーブル名は重複できず、ステージ数は 8 までです。

各中間結果は 100,000 行までです。

これは有界なカーディナリティとインデックス有無による戦略選択器であり、完全なコストベースプランナー、完全なインデックス対応結合プランナー、ストリーミング実行器ではありません。

単一テーブル HTTP サーバーは結合を公開しません。

カタログサーバーは `QUERY /join` で同じ読み取り専用境界を公開します。

テーブル間の書き込みとトランザクションはこの境界の外側です。

結合は既存の `filter` と `projection` の規則を受け付けますが、`sort`、ページング、集約、自己結合エイリアス、テーブル間トランザクションは受け付けません。

MongoDB の [`$lookup` ステージ](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/)を語彙の参照にします。

MongoDB は `$lookup` を一致する外部文書を配列として追加する左外部結合として説明しますが、txBASE は付属する結合計画に合わせてフラットな関係行を出力します。

MongoDB の文書は、外部側にインデックスがない結合の性能コストも説明しています。

そのため最初のスライスには結果数の上限を設け、プランナーレベルの性能を主張しません。

## 4. 現在の述語語彙

| 分類 | 演算子 | 現在の規則 |
| --- | --- | --- |
| 比較 | `$eq`、`$ne`、`$gt`、`$gte`、`$lt`、`$lte` | エンジン固有の型規則でデコード済み JSON 値を比較する |
| 所属 | `$in`、`$nin` | 値を候補値のリストと照合する |
| 論理 | `$and`、`$or`、`$not` | 述語文書を合成または反転する |
| 式 | `$expr` | 同じレコードの二つのスカラーリテラルまたはフィールド参照を比較する |

空の `$and` はすべてのレコードに一致します。

空の `$or` はどのレコードにも一致しません。

欠損フィールドは、現在の実行器契約に従って `$ne` と `$nin` に一致します。

フィールドが配列の場合、配列要素の一つが述語を満たせば一致することがあります。

これらの選択は `src/query/tests.rs` と `src/query/malformed_tests.rs` でテストします。

これらは txBASE の動作であり、MongoDB 互換性として説明してはいけません。

## 5. パス、配列、プロジェクション

ドット区切りパスはネストした JSON オブジェクトと配列をたどります。

数値のパス要素は明示的な配列インデックスを選びます。

数値でないパス要素は配列要素全体から一致するフィールドを訪れます。

完全一致するフィールド名はドット区切りの走査より優先されます。

プロジェクションは選択したフィールドを適用する前に形状を検証します。

現在の実装は MongoDB のすべてのプロジェクション規則、位置指定プロジェクション、`$elemMatch` プロジェクション、集約式を保証しません。
