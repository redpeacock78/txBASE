# ロードマップと明示的な非目標

このロードマップは、提供された設計メモ `txBASE Roadmap: CJK Compatibility, XBF, and Database Evolution` に従います。

提案されたフェーズ順を保ち、実装状態を明示します。

Future と記した項目は現在の機能ではありません。

## 1. 位置付け

txBASE は dBASE と xBase の系譜に属するファイルネイティブなトランザクショナルデータベースです。

DBF は互換性と保存のための表面として保ちます。

提案する XBF 形式は、DBF が損失なく表現できない型とメタデータのためのネイティブ形式です。

HTTP、JSON、MCP、WASM はストレージ形式の上位にあるアクセスまたは実行の表面です。

長期的な設計目標は SQLite や PostgreSQL の置き換えではなく、既存 xBase データの移植性です。

## 2. 現在のベースライン

リポジトリは現在、次を提供します。

- 選択した従来型および Visual FoxPro フィールドの DBF 解析と書き込み。
- サポートする形式の DBT および FPT memo またはバイナリサイドカー経路。
- 小さな MongoDB 風述語語彙による JSON クエリ実行。
- 数値 `$abs`、`$add`、`$subtract`、`$multiply`、`$divide`、`$mod` オペランドを含む、フィールド間比較リーフ上の有界 `$expr` 論理木。ただしテーブルスキャンの参照経路に留まる。
- 有界な JSON Merge Patch と JSON Patch によるレコード更新を含む HTTP `GET`、`QUERY`、`POST`、`PUT`、`PATCH`、`DELETE` ルート。
- `TXOP`、`TXTI`、`TXDP`、`TXDB`、`TXDM` 永続化経路を持つファイルまたはメモリ WAL 型。
- WAL を変更せず、完全なレコード境界と切断された末尾を表示する読み取り専用 `wal inspect` コマンド。
- 保持されたメモリまたはファイル WAL のコミット、ロールバック記録から `TransactionId` 列を再開する低レベルスナップショットトランザクションエンジンと、HTTP 更新境界へ公開する永続的な DBF 単一テーブル WAL コミット ID。
- 起動時復旧、古いスナップショットの拒否、Ubuntu、macOS、Windows の CI ゲート。
- スキーマの内省、DBF 検証、サイドカー対応の backup と restore、検証済み DBF と memo サイドカーのコピーコマンド。

- 複数テーブル更新トランザクション向けの永続的なカタログジャーナルコミット ID。
- 一つのスナップショットまたは WAL コミットで複数のレコード操作を適用する単一テーブルトランザクションエンドポイント。
- 成功した読み取りの強いテーブルおよびカタログ表現 ETag、GET と HEAD の If-None-Match 検証、単一テーブル、名前付きテーブル、カタログ全体のトランザクション経路に対する更新側 If-None-Match 検証、単一テーブル更新、名前付きテーブル更新、カタログ全体のトランザクションの任意の If-Match 保護。
- 0 個以上の `$match` の後に終端 `$count` または `$distinct` を一つ置く、または `$count`、数値のフィールド参照またはリテラルによる `$sum`、数値 `$avg`、`$min`、`$max`、`$first`、`$last`、`$push`、`$addToSet` を使う `$group` を一つ置き、グループ出力の `$match`、最後の `$sort`、`$skip`、`$limit` を適用する有界集約パイプライン。

- 等値、範囲、複合等値プレフィックス範囲の候補検索、ヒストグラムによる範囲順序推定、単一フィールドと順序プレフィックスの走査、フィールド方向ごとの複合プレフィックスソート走査、等値プレフィックス候補数、一様統計による等値候補積集合、レコード数、インデックス走査、ソート作業に基づく有界なコスト選択と非選択的なインデックスをテーブルスキャンへ戻すフォールバック、パス対応計画、DBF と memo の鮮度検査を持つ再構築可能な外部スカラーおよび複合キーインデックスサイドカー。

## 3. フェーズ 1：小さなローカル DBMS を完成させる

このフェーズでは、エッジまたは分散動作を追加する前に、データベースをローカルに保ち、運用上の境界を使えるものにします。

### 候補範囲

- スキーマの内省。
- 複数テーブルカタログの境界。
- セカンダリインデックスの保守とクエリ計画。
- 長寿命ストリーム向けのランタイム固有非同期トレイト。
- トランザクション ID と独立して見える複数レコードスナップショット。
- `PACK` と `RECALL` の保守操作。
- `verify`、`backup`、`restore` のツール。
- 読み取り専用 WAL 検査。

`PACK` は memo ブロックとインデックスを再構築するか、回収可能な孤立領域として残すかを定義しなければなりません。

`RECALL` は削除マーカーだけを復元するか、インデックス更新またはトランザクション更新にも参加するかを定義しなければなりません。

### 完了条件

スキーマの内省、検証、サイドカー対応の backup と restore、コピー、`PACK`、`RECALL`、読み取り専用 WAL 検査、最初のディレクトリカタログ境界は、フェーズ 1 の最初のスライスとして実装済みです。

カタログは現在、直下の DBF ファイル名からテーブル識別子を導出し、別のマニフェストを永続化しません。

テーブル検出、名前付きテーブルのロード、スキーマ出力、テーブルごとの検証、単一テーブルの永続化境界を再利用する独立した名前付きテーブル HTTP 更新を提供します。

リレーション、テーブル間インデックスの協調、MVCC 可視性はまだ提供しません。

インデックスサイドカーの基盤は、スカラーキーとフィールドごとの方向を持つ複合キー、正確な等値と範囲の候補検索、ヒストグラムによる範囲順序推定、単一フィールドの順序付き走査、複数キーソートの順序プレフィックス走査、対応する混在または一様方向の複合プレフィックス走査、等値プレフィックス候補数、一様統計による等値候補積集合、レコード数、インデックス走査、ソート作業に基づく有界なコスト選択と非選択的なインデックスをテーブルスキャンへ戻すフォールバック、パス対応計画、古さの検出、明示的な再構築、通常の永続化後の WAL 付き DBF とインデックスの復旧に対して実装済みです。

完全なコストモデル、照合対応インデックスキー、カタログ全体の MVCC 可視性、過去の行バージョンはまだサポートしません。

残りの項目には、公開契約、壊れた入力の動作、クラッシュ動作、フィクスチャまたは決定的テストが必要です。

現在のカーソルスライスは `page_size` と `cursor` による物理レコードページングとソートキーセットページングをサポートします。

`skip` を拒否し、ページを 1,000 レコードに制限し、物理ページは要求ページと先読みレコードが見つかるまでだけ走査します。

ソートページはキーセット境界を適用する前に一致するレコード参照を具体化します。

新しく発行する物理およびソートカーソルは、バージョン付きテーブル表現スナップショットタグを持ち、テーブル変更後の再利用を拒否します。

タグなしの従来カーソルは互換性の境界として残します。

公開する `query::stream_query` イテレータは、一致レコードを具体化せずにソートなしのフィルターとプロジェクションを処理します。

`query::stream_query_snapshot` はロード済みテーブルの複製を所有し、呼び出し側が pull 型イテレータを消費する間もレコードを安定させます。

`query::stream_query_bounded` は同じスナップショットイテレータを標準ライブラリの有界チャネルの背後で実行し、チャネルが満杯なら生成側を停止し、消費側が drop されると停止します。

HTTP サーバーは `/records/stream` と `/{table}/records/stream` をこのストリーム上の有界 NDJSON chunked response として公開します。

ランタイム固有の非同期トレイトは後続の契約です。

より広いロードマップに対してインデックスを完成と呼ぶには、insert、update、論理削除、復旧、古いインデックスの検出、再構築動作、コストモデルの制限、方向の互換性、クラッシュ動作を一緒に仕様化してテストしなければなりません。

複数レコードトランザクションを完成と呼ぶには、コミット、ロールバック、クラッシュ復旧、可視性規則を一緒にテストしなければなりません。

単一テーブルのトランザクションスライスは、一つのスナップショットまたは WAL 永続化経路を通じて一つの DBF テーブルを対象にします。

カタログトランザクションスライスは、カタログロック下で複数 DBF にまたがる名前付き操作を準備し、DBF と変更サイドカーのイメージをディレクトリジャーナルでコミットし、カタログジャーナルコミット ID を永続化し、次のカタログ読み取り前に不完全な準備を復旧します。

この ID は順序と識別の境界であり、過去の行バージョンと MVCC 可視性は将来の作業です。

低レベルの `TransactionManager` は、これらの DBF 永続化経路とは別です。

その `TransactionId` 割り当て器は、完了したトランザクションレコードを保持する WAL を再オープンした後に継続します。

これは過去の行バージョンを提供せず、HTTP へ ID を公開しません。

## 4. フェーズ 2：クエリモデルを拡張する

クエリモデルを拡張している間も、現在のレコードスキャンを参照実行経路として保ちます。

### 候補範囲

- 現在の有界な group アキュムレータを超える追加の集約ステージとアキュムレータ式。
- 有界 `$expr` 論理木と数値 `$abs` / `$add` / `$subtract` / `$multiply` / `$divide` / `$mod` オペランドを超える完全な式評価。
- 結合。
- 制約。
- 範囲および混在方向の複合経路に対する完全な物理コスト計画。

最初の結合スライスはローカルで有界です。

`full` 等値結合も、有界なハッシュフォールバックまたは互換性のある ordered index の merge 経路で実行し、両側で一致しない行を出力します。

一つ以上の等値条件を実装し、小さなネステッドループの境界を超えると有界なハッシュ、インデックス検索、merge のコストを比較し、推定値が低い場合に鮮度検証済み単一フィールドインデックスを使います。
直接または多段検索ではフィールド順が一致する複合インデックスを使い、大きな直接結合では推定値が低い場合に互換性のある ordered index の merge 経路を使います。
直接および多段検索では、等値条件のフィールド順と完全に一致する複合インデックスも使います。

追加ステージは以前に結合したテーブルを参照でき、パイプライン全体で一つのカタログ読み取りロックを保ちますが、完全なインデックス対応またはコストベースのマージ計画、ストリーミング、null と欠損フィールド意味論は将来です。

分散結合と分散トランザクションは後続の機能です。

集約を HTTP API に追加する前に、欠損、null、数値オーバーフロー、メモリ制限の動作を定義しなければなりません。

現在の集約スライスは、終端 `$count` または `$distinct` を一つ、または `$count`、フィールド参照またはリテラルによる `$sum`、`$avg`、`$min`、`$max`、`$first`、`$last`、`$push`、`$addToSet`、グループ出力に対する有界な `$match` と `$project`、最後の sort、skip、limit を備えた `$group` を一つ許可します。

既存の包含と除外のプロジェクション契約を再利用します。

プランナー説明の境界は `explain_query_at` と `QUERY /explain` で実装済みです。

完全なコストベース選択は将来の作業です。

最初の制約スライスは任意のスキーマサイドカーです。

従来の DBF バイト列を変えずに、単一フィールドの `primary`、`unique`、`not_null`、有界な複合 `primary` と `unique`、省略された insert のスカラー既定値、アクティブレコードと更新候補に対する有界なテーブルレベルクエリ述語 `checks` を強制します。

カタログスコープの `references` 検証は非 null の子値をカバーし、子を孤立させる親の更新または削除を制限します。

スキーマ移行と、より広いテーブル間制約は将来の作業です。

## 5. フェーズ 3：従来型の国際互換性

文字デコードとソートは別の契約です。

このフェーズでは DBF のバイト幅を保ち、曖昧な書き込みや表現できない書き込みを拒否しなければなりません。

### 候補範囲

- CP932 または Windows-31J。
- strict Shift_JIS の区別。
- EUC-JP。
- GBK と GB18030。
- Big5。
- CP949 と EUC-KR。
- 明示的なエンコーディングオーバーライド。
- 照合。
- 追加の上流 CJK フィクスチャ。

各エンコーディングには、宣言名、バイト幅規則、往復フィクスチャ、不正バイト動作、比較方針が必要です。

最初の宣言ドライバースライスは、DBF 互換性文書に記載した四つの Visual FoxPro CJK ID と、そこに記載した legacy dBASE alias をカバーします。

壊れた読み取りには置換文字を使い、表現できない文字または幅を超える書き込みを拒否します。

サイドカーとパス対応 CLI は、四つのコーデックに加えて strict Shift_JIS、EUC-JP、GB18030、ISO-2022-JP の明示的なオーバーライドを提供します。

後者の四つは DBF 言語ドライバーへの対応付けを主張しません。

スキーマ出力は宣言名と実効名、解釈元を公開します。

strict Shift_JIS は ASCII、半角カタカナ、JIS X 0208 を受け付け、CP932 拡張を読み取りで置換し、書き込みで拒否します。

固定DBFフィクスチャは四つの Visual FoxPro CJK ID と legacy dBASE の `0x4d` ID をカバーし、マルチバイトレコード値を往復します。
alias testはlegacy alias全体をカバーします。

上流 Visual FoxPro の Windows-1251 フィクスチャも、キリル文字のレコード値を往復します。

固定した明示コーデックのバイトフィクスチャは、サポートする八つの明示コーデック名についてDBFレコードのデコードと書き込みの往復をカバーします。

クエリ層には有界な `unicode-lowercase` ソート照合があります。

ロケール対応 CJK 照合と、追加のより広い上流 CJK フィクスチャは将来の作業です。

上流の JavaDBF GBK フィクスチャは、GBK でエンコードされた三つの CJK フィールド名と 28 件の実データをカバーします。

読み取り、更新、バイト列の往復も検証します。

上流の Rust `dbase-rs` CP936 フィクスチャは、legacy dBASE の `0x4d` driver ID を含み、読み取り、更新、バイト列の往復を検証します。

上流の SeoulTech Korea Maps EUC-KR フィクスチャは、韓国語のフィールド名、16 件の実データ、legacy dBASE の `0x4e` driver ID をカバーします。
読み取り、更新、バイト列の往復も検証します。

同じ出典には、四つの韓国語フィールド名、232 件の実データ、legacy dBASE の `0x4e` driver ID を持つ市区町村単位の EUC-KR フィクスチャもあります。
読み取り、更新、バイト列の往復も検証します。

クラシックな DBF フィールド記述子名にも実効コーデックを使うため、CJK の列名を JSON 参照と更新で利用できます。

記述子の上限は引き続きバイト単位で、XBF 出力では ASCII のフィールド名だけを受け付けます。

オーバーライドは、読み手が同じ解釈を再現できるようスキーマまたはコマンド出力に見えなければなりません。

## 6. フェーズ 4：ネイティブ XBF

XBF は黙って DBF を拡張するものではなく、独立してバージョン管理するネイティブ形式です。

v1 のワイヤー契約は [XBF v1 フォーマット草案](xbf.md)にあります。

有界コーデック、表現可能なフィールド単位のスキーマ制約を保ち未サポートのメタデータを拒否する DBF から XBF への変換ヘルパー、有界なメモリ内およびスキーマサイドカー付き XBF から DBF への出力、表現可能性レポート、耐久スナップショット経路、世代検査付き完全スナップショット WAL 復旧、`TXSE` によるスキーマ保存ファイル出力ジャーナルは、この草案に対して存在します。

`TXSE` は基底バイトを記録し、次の DBF 読み取り時に中断された DBF、スキーマ、memo サイドカー、トランザクション状態の置換を復旧し、外部から変更された対象を拒否します。

厳密な複数ファイル読み取りアトミック性とオブジェクトストレージコミットの意味論は将来の作業です。

提案するマジックは `TXBF` です。

提案するメディアタイプは、形式仕様の確定後も登録が適切なら `application/vnd.txbase.xbf` です。

### 候補範囲

- XBF v1 仕様。
- UTF-8 テキスト。
- 明示的な `NULL`。
- 可変長文字列。
- 現代的な整数型。
- タイムスタンプ。
- バイナリと blob 値。
- 損失のない DBF から XBF への変換。
- 検証済み XBF から DBF への出力。

最初の形式では、ヘッダー、チェックサム、破損処理、バージョンネゴシエーション、ダウングレード動作を定義しなければなりません。

DBF 互換性は明示的なインポートまたはエクスポート経路として保ちます。

## 7. フェーズ 5：エッジストレージ

範囲指向のローカルストレージ抽象化は出発点として有用ですが、オブジェクトストレージには不変オブジェクトと条件付きマニフェスト更新が必要です。

### 候補範囲

- ストレージバックエンドの再設計。
- WASM 対応コア。
- R2 またはオブジェクトストレージアダプター。
- マニフェストの compare-and-swap コミット。
- 不変ページ。
- 世代スナップショット。

オブジェクトストレージモデルには、一貫性契約、孤立ページの掃除方針、再試行動作、決定的なローカルフィクスチャが必要です。

WASM は二つ目のデータベース実装を作らず、DBF または XBF コーデックとクエリ契約を再利用しなければなりません。

## 8. フェーズ 6：高度なデータベース機能

分散動作は、ローカルとエッジの契約が安定してから追加します。

### 候補範囲

- 完全な MVCC。
- 変更データキャプチャ。
- 永続 WAL 履歴。
- レプリケーション。
- Raft または明示的に選択した別の権威プロトコル。
- スナップショットインストール。
- follower 読み取り。
- 分散パーティショニング。

これらの機能には、権威モデル、競合意味論、スキーマバージョン処理、復旧手順、可観測性が必要です。

現在の排他的テーブルロックから、コンセンサスやマルチリージョン機能を推測することはできません。

## 9. XBF と共有する上位層

DBF と XBF のコーデックは、意味論が一致する範囲でクエリ、トランザクション、HTTP、ストレージのインターフェースを共有すべきです。

形式固有層だけが、バイトレイアウト、フィールド変換、チェックサム、復旧レコードを所有します。

これにより XBF が無関係な二つ目のデータベース実装になることを防ぎます。

## 10. ファイル粒度の規則

所有者、失敗時の動作、テストフィクスチャ、変更頻度が異なるコードはファイルを分割します。

現在のリポジトリは、DBF コーデック、memo 処理、WAL 差分、クエリ検証、サーバー範囲、テストグループをすでにその境界で分けています。

クエリ契約、プランナーの根拠、更新契約は、所有者と将来作業が異なるため別の文書に分けています。

さらに分割する場合も実際の境界に従います。

ファイル数それ自体は品質指標ではありません。

## 11. 現在のスライスに対する明示的な非目標

- dBASE コマンド言語の完全互換性。
- Visual FoxPro ランタイムの完全互換性。
- MongoDB ワイヤーまたは BSON 互換性。
- Firebase の認証、セキュリティ規則、リスナー、オフラインクライアント。
- SQLite と同じテスト量またはカバレッジの主張。
- 宣言エンコーディングが曖昧な場合の自動 CJK 変換。
- 契約とエンドツーエンドテストなしの完全なコストベースプランナー、結合、集約、MVCC、耐久 XBF、オブジェクトストレージ、分散コード。

現在のインデックススライスは意図的にローカルです。

対応する複合方向、等値プレフィックス候補の選択、レコード数、インデックス走査、ソート作業に基づく有界なコスト選択は実装済みですが、I/O を考慮した完全なモデルとテーブル間協調は将来の作業です。
